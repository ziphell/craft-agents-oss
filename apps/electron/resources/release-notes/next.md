# Pending Release Notes

This file accumulates release notes for the next unreleased version. PRs that add user-visible behavior should append a bullet to the relevant section here. Versioned files (`X.Y.Z.md`) are owned by the release skill — never create them in feature commits. The in-app loader only reads `X.Y.Z.md` files, so this file is never shown to users.

## Features

- **The Web UI has its own password, and the hub's credentials became records it can retire one at a time** — every caller used to authenticate with `serverConfig.token`, which also doubled as the Web UI's login password and cookie key: rotating it signed every browser out, and no caller could be revoked on its own. The Web UI now has a password of its own (generated the first time Server Mode runs, shown and resettable in **Settings → Server**), and the login page accepts either that password or the server token — both already drive the hub, so this adds no privilege. Session cookies are signed with a key **derived from both**, so changing either one ends existing browser sessions; like port and TLS, that is read at startup, so it needs a restart. Behind that, credentials are records with a scope: `client` is a full client, `device` is a machine that only answers capability calls and may not drive the hub (`SCOPE_FORBIDDEN`), `both` is the server token. Revoking a record takes effect at once — new handshakes fail, and its live connections are dropped and not held for replay. Devices now have a token of their own: **Add device** in **Settings → Server** creates a slot whose token stays visible and copyable in the device list until a machine claims it, the first real handshake binds that slot to the machine's `deviceId`, and from then on it works only there — it never expires and cannot be moved to another machine (removing the slot is the way to start over). **Test Connection** does not claim it: the hub answers a probe with the token's scope and keeps no client record, so device access and allowed folders are still chosen before the connection is saved; the save's first handshake is what binds the slot and carries them. The hub keeps a hash, plus the pending token until it is claimed; removing a slot deletes the record and drops its connections, while the client keeps reconnecting with the same token. The server token is no longer shown in the UI, returned by the settings RPC, or rotated on its own — it is what this machine's own windows present, and every other machine connects with its own slot. On a headless server `CRAFT_WEBUI_DIR` supplies the bundle, `CRAFT_WEBUI_PASSWORD` overrides the generated password, and a generated password is printed once at startup.

- **The browser has profiles, and a profile is a window** — the browser window used to keep **one** set of cookies for the whole app, so two accounts of the same site were impossible: signing in to one signed you in everywhere, and a login made for one piece of work was a login made everywhere. The browser now has **profiles** — named Chromium sessions, each with its own cookies, `localStorage`, caches and logins. The built-in **Default** profile keeps the session every login already lived in, so an upgrade changes nothing about what you are signed into. A workspace can name a default profile, a project can name its own in the project's settings (below the working directory; left empty it follows the workspace), and a conversation can override both — the same chain the model picker uses: the conversation's pick, the project's default, the workspace's default, then Default. A profile is a **window**: one workspace holds one window per profile in use, so two accounts of the same site are two windows, each with its own tabs (numbered from `tab-1`) and its own address bar, rather than one tab strip holding two accounts. Switching a conversation's profile changes the profile its composer, top-bar badge and prompt name, and where its unnamed commands work — while the tabs it already had stay where they are, because a live page cannot have its cookie jar changed underneath it. **Settings → Browser** is where profiles are made, renamed and deleted — `Default` is built in and cannot be removed, and deleting a profile leaves its cookies on disk — while a workspace's default lives in its own settings and the composer has a profile picker beside the model picker (it appears once a second profile exists). The top bar has **one browser control**: it shows the browser window for the conversation's profile with the tab in use, and a globe when that window is not open — never the profile's name twice, and never following whichever window the person last clicked, because attention is not a profile choice; its menu lays that profile's window out flat with its tabs, holds every other window as a submenu, and lists the profiles that have no window yet — a click opens that profile's window. Once a second window exists, each window's name in the OS's own lists (taskbar, alt-tab) is simply its profile's.

- **A conversation can drive two browser profiles at once** — `browser_tool` reaches every profile: `profiles` lists them (name and id), and any command takes `--profile <name-or-id>` to work in that profile's window, opening it when it is not up. A command that names none uses the profile the conversation is set to — its own pick, then the project's default, then the workspace default, then Default — and does not fall back to Default while another one is selected; a name that does not exist is refused rather than mapped to Default — so an agent can sign in to two accounts in one task by naming a profile on the commands meant for it. `tabs` lists every profile's window, grouped and labelled, because a tab id is unique inside one window and two profiles can both hold `tab-1`. Spawned sessions inherit the parent's browser profile the way they inherit its working directory, so a task's nodes stay in the profile their orchestrator is working in. Switching the conversation's profile applies to the next browser command, and the profile is part of the conversation's volatile context, so the agent knows where it is working and that the user moved it without the cached prompt prefix being re-stamped.

- **The browser window grants every permission a page asks for, so an automated flow never stalls on a dialog** — there is nobody at the window to answer a permission prompt, so a page that asked for one waited forever. Camera and microphone, geolocation, notifications, clipboard read and write, pointer lock, fullscreen, window management, idle detection and the rest are now granted outright, with no prompt and no per-site memory: a page probing a permission sees it as granted. Screen capture is the one thing left bounded, and the bound is on the **source** rather than the permission — a page may call `getDisplayMedia`, but it is answered with **its own tab** (Electron's tab capture) and never the desktop, a window or another tab, so a page can record itself and nothing beyond it. The record button's own request is the only one answered with a different tab: the one a person armed, and an empty answer when nothing is armed.

- **The app lives in the tray, and closing the last window puts it away** — closing a window no longer quits the app: it stays running with a tray icon. With more than one window open, closing one really closes it, the way a browser's or an editor's X does, so windows never pile up hidden; the **last** window is hidden instead, keeping its state (panels, scroll, a half-typed draft) exactly where you left it. **Left-clicking the tray icon brings the app back**, and the menu — one entry per workspace (focus its window, or open one if it has none) and **Quit** — is on the right button (on macOS the click itself is the menu, the way a status item's is). That **Quit** is now the *only* way to quit on Windows and Linux, where the app has no native menu bar; on macOS the dock does the same thing, and the tray is there too. Launching the app reopens **every window that was still open** — local windows and windows connected to a hub alike, each restored to the view and the size it had, with the one you were last in on top; a minimized window comes back too. The same window comes back from clicking the tray, clicking the dock, or double-clicking the app while it is running. Quitting is only ever an explicit act — the tray's **Quit**, or Cmd/Ctrl+Q. Where a tray cannot be created the old behaviour stands (the last window closing ends the app), so the app can never end up running invisibly with nothing to bring it back. The tray is present in every window — local and connected to a hub alike — and never in a headless server.

- **A link opens the app's own window** — a path or an address in a conversation used to be either a file the app showed you or a link it handed to your browser; it is now something that opens where the conversation can carry on with it. A `.drawio` path opens the diagram window (the same one a `drawio-preview` block opens, on that diagram). An `.html` path is drawn in the app's own preview window — the same window an `html-preview` block opens full screen, frame and all — and that window's header has an **open in browser** button for when drawing the file is not enough: it opens the same file as a real tab in the workspace's browser window, where its own scripts run and its stylesheets, images and second documents resolve against the folder it sits in, neither of which a frame can give it. A row on the project page's **Goal, Specs & Plans** tab is the same click: the document opens in the app rather than in another program. An **http(s) link goes to that browser window by default**, so it arrives as a tab the conversation can pick up (snapshot, click, a screenshot) rather than somewhere outside the app — and it opens **in the profile that conversation works in**, so a conversation with a profile of its own keeps the page in the window its `browser_tool` commands land in; a link clicked outside a conversation uses the workspace's default profile. **Settings → Links** is where a link and that button go to your own browser instead — one switch, because which browser is the person's is one question, and the app's window is the one an agent can keep working on. Two things worth knowing about a file opened in a browser. It has an origin of its own and no more: no ES modules, no `fetch` of the file beside it, no `localStorage` — a page that needs those wants an address rather than a path (a website has one). And a link inside it that asks for a new window is refused, because the window opens what a link points at as tabs and has nowhere to put a bare one. The `html-preview` block is unchanged: HTML drawn in a message, scripts off — and the full-screen window it opens carries the same **open in browser** button.

- **A project's diagram is a drawio file the app both draws and edits** — a `.drawio` file in a project's folder is now a diagram like any other material: a `drawio-preview` block naming it (`{"src": "…/checkout.drawio", "title": "Checkout flow"}`) renders it with drawio's own viewer, together with the same full-screen button the HTML preview block has, in the same corner with the same reveal — and a pencil, which opens drawio's editor on that diagram in the **full-screen window** rather than turning the conversation into a canvas. A drawing is shown at **the size it was authored** — labels at the size they were drawn, in the conversation and full screen alike — so a drawing wider than its box is never shrunk to fit it. A diagram in a conversation then scrolls, as mermaid's does (a drawing only a little too wide is the exception, and is fitted, because a strip of scrollbar costs more than that much of the picture); the full-screen window pans instead, and has no scrollbar to explain anything. The window is where the zoom is: the wheel, −/+, a percentage to pick a size from (25% to 400%, with **Fit** and **Reset**), and `⌘+` / `⌘−` / `⌘0` — and a zoom holds its place, following the pointer under the wheel and the middle of the box for the buttons. **A mouse drag moves the picture** rather than selecting the labels it passes over — the gesture a conversation and a window share — and a double-click puts it back in the window, where a click has nothing else to do. Editing opens in the full-screen window — the pencil on a diagram in a conversation. A page works the same way: the pencil on an `html-preview` block opens the editor on it, so there is one page editor rather than two. Editing works **on the file, not on a copy** — every change is written back to the same path about a second after you stop typing, including the change still pending when you close the editor — and two things follow. Saving is bounded by the same rule that let the app show you the file: **whatever it could open for you, you can save**, so a diagram or a page outside this workspace still saves rather than reporting a refusal. And the editor is not the only writer: a conversation can edit that same file while you have it open, so a save re-reads first, and a write that arrives while the editor is open is seen **when it happens** rather than at the next save — with nothing drawn yet the editor follows the file and redraws, and once something has been drawn it asks which version wins instead of silently overwriting either. That also works the other way round: a diagram shown in a conversation redraws when the file changes, so an agent's edit arrives as a picture rather than as a description of one.

  Offline is why the editor ships with the app rather than loading from a CDN. Both the viewer and the editor are a pruned copy of drawio's own web application — 74 MB of a 148 MB release, with the template browser, the cloud-drive integrations, the servlet descriptors and, unless you ask for them, 41 MB of raw shape data left behind — fetched by `bun scripts/fetch-drawio-assets.ts` rather than committed, and served at an origin of the app's own. The shape data is the one part worth knowing about: it is not installed by default, and a diagram using a shape set drawio does not bundle (Azure or network icons, say — usually one that came from elsewhere) draws those shapes as plain boxes rather than saying anything, so `--full-stencils` is how you get them. The viewer's own document is pinned to that origin and nothing else, which is what makes "a diagram cannot reach the network" a property rather than a promise; the editor is drawio's own application and cannot be pinned the same way, so it is *asked* to stay offline (`offline=1`, the switch drawio's desktop build pulls). Nothing about a diagram is exported, packaged or uploaded, and the `.drawio` file remains the artifact that travels with the folder it lives in.

- **An HTML preview can be edited where you are reading it** — an `html-preview` block gets the same pencil the diagram block has, in the same corner with the same reveal, and it opens the page in the **full-screen window** rather than turning the conversation into an editor. Click an element to select it, double-click it to retype its text, and the controls that appear on it do the rest: bold, italic, underline, strikethrough, text size, delete the selected element, and undo/redo — a page editor without undo is not one. Clearing an element's text deletes the element, because an empty box left behind is a hole in the page rather than an edit. **The page does not move when you open the editor**: the same document is drawn again in the same frame at the same size, and the offset you had scrolled to comes across with it. The controls are a small bar **on the selection** — just above the box you selected, below it when there is no room above, following it as the page scrolls — so they come and go with what they act on instead of taking a strip of the page. The element's name is on a chip at the page's own bottom-left corner, which is where the element picker puts its chip and out of the way of the thing it names. **The file is what changes.** An edit is written back to the same path about a second after you stop typing, including the change still pending when you close the editor, and it is written as a **change to the span you touched** rather than a re-serialization of the document — the file keeps its own indentation, comments and quoting, because it is a file somebody wrote, not the output of a formatter. The element's own markup can also be **sent to the conversation** in one press, as a reference that names the file and quotes the element: it goes into the draft, appends to whatever you were writing and sends nothing, so you say what should change. There is deliberately no "rewrite this with a model" button here — the model the app has is the conversation, and pretending otherwise would need a second one.

  Two things about the editor are worth knowing, and both are about what it is *not* allowed to do. The preview you were reading stays exactly what it was — a frame that runs no scripts and cannot reach the app — while the editor needs a probe inside the page to draw the selection and report what changed, so it uses a **second frame with a different sandbox**: scripts on, and an opaque origin, which is why the page still cannot see the app that is editing it, and why everything the editor knows arrives as a message and every edit is applied to the file rather than to the page. And because the writer here is a person editing a file the app just showed them, saving is not the agent's write policy: it is bounded by **the folders this workspace is made of plus the folders its open conversations work in**, so a report a conversation wrote in your project folder saves where it sits, and a path outside all of them is refused with the refusal rather than quietly written somewhere else. A page whose own `Content-Security-Policy` forbids inline scripts cannot host the probe at all; that is reported instead of leaving something that looks editable and is not.



- **A command can name a file instead of pasting its source** — `browser_tool` takes `--file <path>` on `evaluate`. `evaluate --file scripts/probe.js` runs a local script in the page: the file is written once (with the Write tool) and the same code never has to be produced a second time inside the command, nor re-escaped through the command string. A relative path counts from the workspace root, `~/…` is expanded, a BOM is dropped, and the answer says which file it ran and how many characters that was; over 256 KB is refused rather than shipped. It is a probe and says so — what it runs is not registered, so a reload drops it. The flag exists for one reason: an agent iterating on a script was generating the same source twice per round and paying for it in context.

- **`reload` — the tab a conversation works from, reloaded** — there was no command for the reload an agent kept asking for, so it could only `navigate` to the same address and hope. `reload` acts on the tab the command acts on (your tab, or the one `--tab` names), like the browser's own reload button — fire-and-forget, so it returns as soon as the reload is asked for rather than pretending the document is loaded: it says which URL it is reloading, tells you to `wait network-idle` (or wait on a selector) before reading the page, and that every `@eN` ref from before is stale. A batch stops at it for the same reason it stops at `navigate`.

- **Element picker for browser_tool** — new `pick` command: the agent asks you to click an element on the page and gets back a stable selector (`data-testid` → `id` → `:nth-of-type` path) plus tag, text and viewport rect. Cancel with Escape or `--timeout <ms>`. Runs through the existing CDP session, so it needs no permission changes and stays sandboxed.
- **A project's folder holds up to three tiers of the same work, and a conversation says which tier it is in** — a specification used to be a workspace-level thing called a prototype, with a folder of its own and a tool of its own; a project's work is now three tiers of file in the project's own folder, the same work at three levels. `goal.md` is one per project and says why the project exists; a `*.spec.md` is one per requirement and says what is wanted; a `*.plan.md` is one per requirement and says how it will be done. **The file's path is its identity**, and **two files that share a stem are two tiers of one piece of work** (`cart.spec.md` and `cart.plan.md`), so the tiers gather around that stem with no index or pointer file needed to keep them together. `spec.md` at the root is the conventional entry — an **index**, not a spec — and nothing seeds it, so a project folder starts with **no specs**. What a spec is, is the file's **name**, not its format: a research report, `notes.md` or a `README.md` beside the specification is material, even if it carries a heading that looks like a spec, and what sits beside the specification is yours — personas, the flow as it stands today, a glossary, a screenshot of the old screen — any format, any number of files. A conversation says which tier it is working in through a **mode selector in the composer's `+` menu — Goal, Spec or Plan, or off** — which appears only for a conversation that is in a project, because the project's folder is the only thing it has to point at, and **one tier is chosen at a time**: they are stages of the work rather than switches that can be on together, and the one selected puts its rules in front of the agent for the rest of the conversation. The tiers are told apart by what each is allowed to say. A **spec** says what is wanted and **nothing about how** — no stack, no API, no code structure. A **plan** says how and **may not change what the spec asks for**; to change that, go back and change the spec. A **goal** says only why the project exists, and writes no detail. **The plan is the last tier of thinking** — the steps, and then the work is built, with what comes next handed to the task system. **Nothing claims an implementation**: the folder is the work, and the report says what the folder holds rather than guessing which file builds which spec. A spec another project holds is reached by an ordinary markdown link that leaves the folder, and a link that points at nothing is reported.
- **Documents point at each other, with ordinary markdown links** — a specification that outgrows one file can index several, and there is no new syntax to learn: `[the checkout flow](docs/checkout.md)` is a link here *and* in every other reader (a colleague's editor, GitHub), which is the same argument that made a diagram's picture plain `![]()` rather than a fence only this app draws. A relative destination is read from the document it is written in, then from the folder — `../spec.md` works too. Opening one is a click, and a relative link opens from **that document's own folder** — the rule a picture already followed — and a link that points at nothing is reported on the project page. It is **navigation, not a claim**: pointing at a document marks nothing done, and nothing in the folder marks anything done. A link inside a code span or a fenced block is an example rather than a link.
- **What a project keeps in view is a document you write, not a list the app keeps** — a project used to record what its work was built against as a maintained list of targets (`prototype-reference <target>`, with `list` printing `references:` / `referenced by:`, a References section on the page, and a block in every bound session's prompt). That tier is gone. It was a set of pointers **nothing pointed back at**: the only failure it could report was "this path is not on disk", which is a spell-check, and what it recorded — *this is what I studied* — is something a file in the folder can say instead; the one affordance it owned (click through to another spec) is a click away in the folder anyway. What replaces it is the folder you already have: a file beside `spec.md` — `references.md`, or whatever you call it — carrying a competitor's address, the path to a screenshot or a design file, or another project's spec, in the folder like any other material.
- **Recording a tab, from the window itself** — the browser window's toolbar has a record button: press it and the tab on screen is recorded to a **video file**, press it again and it stops. It exists because "now" is the one thing no agent can supply from inside the thing being recorded — the person drives the page and the recording follows them, which is what the agent-only `record` command (start/stop, frames) could never do and why that command is gone. **mp4 (H.264)**, the one container: mp4 is what everything else opens (QuickTime, Windows, a browser tab), and — measured with a probe rather than assumed, `apps/electron/spike/recorder-formats.cjs` — it is the one whose length a `<video>` knows the moment it loads, which is what `video_tool sample` works its sampling step out from (a webm recorded live reports `duration: Infinity` until something reads the file out). The file lands in the **downloads folder** — the same place a download from this window goes — named by the minute it started, with a second recording getting a `-2` rather than overwriting the first. Deliberately neither a session's nor the workspace's: the window is one per workspace and a tab's owner says who *opened* it, not who the recording is for, so the file is simply the person's own and a conversation gets it the way it gets any file — by being told where it is (`video_tool sample` is what turns one into frames you can look at). Nothing is sent to any conversation about it: the button says where it went. While recording, the button is a stop button with a running clock, and it goes back to a plain button on its own if the recorded tab is closed — with what was captured kept, since part of it happened. The picture comes through Electron's display-media handler, armed only while a recording is running, so no page can capture a click's worth of the screen; a recording that never got a picture is deleted rather than left behind as a file that shows nothing.

- **A recording's length is measured before it is sampled** — `video_tool sample` works its sampling step out from how long the recording is, and a file written live does not always carry its own length: a webm straight out of `MediaRecorder` (the format browsers reach for by default, and any browser demo that records one) reports `duration: Infinity` until something reads it out. Treated as a step size that is not a coarse sample but a different program, so it is resolved first — asking to play past the end is the one way to make the browser read the rest of the file out — and a recording that still will not say how long it is is reported as such rather than guessed at.

- **Sample a recording into frames** — `video_tool sample <path>` reads a video recorded elsewhere (a phone, Loom, QuickTime, a screen recording of a live session) and hands the frames back **as images in the reply**, because what reads a recording is a model and a directory of files is something it never sees. Decoding is Chromium's — the browser the app already ships, so there is no ffmpeg to install — so a codec it cannot read (ProRes; HEVC on a machine with no hardware decoder for it) fails with a message that says so. `--every 2s` sets the interval, `--changes` keeps only the moments that moved, `--max 40` caps the frames and reports when it hit the ceiling. It writes nothing unless you pass `--out <dir>`, which keeps the frames as `frame-0001.jpg`, `frame-0002.jpg`, …; the recording itself is left where it is. Nothing about the tool is specific to a project: it is a recording, looked at, and a spec can cite a frame the way it cites any other file.

- **"Add to conversation" from the element picker** — the pick button turns selection **on and leaves it on**, and picking something is two steps. **Click an element and it is selected**: a solid box with its selector, staying where it is until you click another element, while the box that follows your cursor — dashed and lightly tinted — is only a preview of what a click would take. Both are drawn in your theme's accent colour, and the element's own name is on a chip of it — one chip, **fixed at the page's bottom-left**, out of the way of the thing it names and in the same place whatever you hover or select (with several selected it lists them, each with its own box to point at it). Then the **"Add to conversation" button under the selection** puts that element in the composer as a **chip** — adding is only ever that button, so a stray click cannot send anything anywhere. Move to another tab of the window and keep picking: any page's elements can be selected, and each one carries the page it came from. It ends when you say so: Escape in the page, or the button again (the button shows the mode the window is actually in, so an Escape is reflected there too). Adding appends: a draft you were writing survives, and the chip shows what the element says, with its selector and its page on hover. When you send the message the chip is rewritten into a readable reference that says which page it was picked on, so what the model reads is a sentence rather than an internal marker — and a message with no text but a chip still sends. It needs no bound conversation: the element goes to the conversation you are looking at, and if this workspace has none, one is opened for it.

- **A whole tab can be put in a conversation, not just an element of one** — the reference below, for a tab instead of a thing on it: "look at this page" is worth saying about a window somebody else may be driving, and a tab named as a chip needs no describing. Two ways in. In the top bar, **right-click a tab** in the window's tab list and choose **Add to conversation**. Or type `@` in the composer: the window's tabs are listed under **Tabs** — the title, with its address beside it, so two tabs with the same title are told apart — and picking one inserts the chip. It goes where a picked element goes, the conversation you are looking at, and the window is left exactly where it is. On send the chip is rewritten into a sentence naming the tab and its address, so the model reads a reference rather than an internal marker.

- **A window holds more than one tab** — opening something no longer replaces what the window was showing: `tab-new` and an address typed into the address bar each open a **tab of their own**, so two pages can be worked on side by side instead of one at a time. Every window has a **tab rail down its left edge**, running the full height of the window with the address bar to its right — the back button and the address start where the tabs end. It holds one row per tab with its title, the tab on screen raised, a close button on each, and a `+` for a new one — always, including with a single tab, because that `+` is how you open something yourself; the tabs are the topmost thing in the window, so nothing covers them. It is a column and not a row across the top on purpose: tabs are a list that grows with use, and a row has to share its width with the address bar — a second tab scrolled the bar aside and pushed the tabs after it out of sight. The chrome's colours are the app's throughout: a tab that paints itself dark no longer repaints the address bar and the rail beside it (the window's own chip in the top bar still takes the tab's colour, which is about *which* window it is). The window's badge in the top bar lists the same tabs under it (marked with a count), so a window that is not in front can still be switched tab by tab. `tabs` lists them for the agent, `tab-new <url>` adds one, `tab-close <id>` closes one (closing the last closes the window), and any command can name the tab it acts on with `--tab <id>`. Naming a tab is a **target, not a request to move you**: the command acts on that tab wherever the window happens to be showing, and `tab-show <id>` is the command that brings one up for you to look at. A window that has just been created is opened *into* rather than beside: its own blank tab is what a window is made of, so a freshly opened page is one tab, not two.
- **The browser is one window per workspace** — every conversation in a workspace, and you, now share a single browser window, with each one a **tab** instead of a window of its own. Ask two conversations to look at two different sites and they end up side by side in the same window rather than in two windows; open a tab by hand and it lands in that same window. It is not tied to any project: the same window is where a general task's browsing happens. `browserPane` resolves the workspace's window for everyone, so "which window is mine" stopped being a question — a window now carries only *who is driving it at the moment* (a lease, renewed by every command and released when a turn ends). Two things follow: who is driving a window is a **lease** (`driven by`, per tab in `tabs`) rather than a lock — the window is shared, so there is nothing to lock — and `tab-close <id>` on that window means "close the tabs you opened" rather than closing it, which is what "don't close the user's things" means once the window is everyone's. Workspaces stay apart: each has its own window. The agent's `windows` command is gone with it: there is one window per workspace, so there is nothing to list (`tabs` answers the tab-level question, and the app's own window list is in the top bar).
- **Opening a browser opens a tab** — the top bar's "New Browser Window" is now "New tab", since there is only one window to put it in. A tab the agent opened in this window is marked with a small icon in the tab rail.
- **Each tab says what it is, who asked for it and who is driving it** — `tabs` prints, per tab, what the tab itself reports (its real address, its title, whether it is loading) and, separately, what is stated about it: `belongs to: …` or `nobody's`, and `driven by: <session>` or `nobody right now`. The three are kept apart on purpose — one is measured, one is intent, one is a lease (who is working on this tab at the moment, released when their turn ends) — and the first two are what let a conversation tell its own tabs from everybody else's. Tabs the agent opened are marked with a small icon in the window's tab rail, and a tab some conversation is working on right now gets a dot.
- **A conversation can only work on — and close — what is its own** — the tab-level half of "don't touch other people's things". A tab is yours to work on when it belongs to nothing (an ordinary tab: anybody's, which is what "you open it, the agent takes over" means for a tab that has nothing to do with anyone's work), when it belongs to the work this conversation is part of, or when this conversation opened it. Another conversation's work is refused, and the refusal names it. Closing is narrower still: only tabs **this conversation opened** — the user's tabs and another conversation's are not yours to close however convenient it would be. `tab-close` on the shared window therefore stopped being a flat refusal: it closes the tabs you opened (the last one takes the window with it) and says so, while the window itself stays — it belongs to the workspace.
- **A link that wants its own window opens a tab beside the one that asked** — `target="_blank"`, `window.open`, popups and a page's own links all become **tabs of the same window**, inserted right after the tab they came from, instead of bare Electron windows with no toolbar. Which kind it was is recorded per tab (`opened as: a popup (no window.opener here)` / `a link that wanted its own window` in `tabs`), because there is one cost worth being able to name: a tab opened this way has no `window.opener`, so a popup waiting for a `postMessage` from the tab that opened it — Google's sign-in is the usual example — will wait forever. Such a tab also cannot close itself (Chromium only lets scripts close windows that scripts opened), so it stays in the tab rail until you or the agent closes it. **Where it lands follows whether the tab is being driven**: while a tab is held by a conversation or a command of its is in flight, anything that opens a tab from it lands **behind** — including a scripted `window.open`, which reads no modifier keys at all — while a link you click in a tab you have taken back comes forward, as in any browser. Nothing has to guess who was clicking.

- **A shared window shows whose tabs are whose** — the tab rail sections its tabs by who opened them: your own under *You*, and one section per conversation (named by that conversation's title) for the tabs an agent opened. The same sections appear in a window's tab list under its badge in the top bar, because both draw the same rule. Headers appear only when there is more than one group — with everything yours there is nothing to tell apart — and tabs keep their order, so the sections read in the order the tabs were opened. It is a view and nothing more: whose tab it is remains the tab's own record, and no rule about what you or an agent may touch changed.

- **The tab being worked on is locked — the window is not** — while an agent works on a tab, that tab takes no clicks or keystrokes, and another conversation's command that names it is refused until the turn ends. Everything else stays yours: the tab rail, the address bar, the window's size, and every other tab. It is the same lock this used to put on the whole window, one level down — a window is shared by the whole workspace, so holding the window held your own browsing and everybody else's tabs with it. The locked tab is marked in the rail and named in `tabs` (`locked: <session> is working on it`), and you are never stuck behind it: that mark in the rail is a **button**, and clicking it lets go (the agent keeps its turn and may take the tab again on its next action). The lock is dropped automatically the moment the tab it holds goes away, so it can never point at something that no longer exists.
- **A conversation works from its own tab, not from whatever you are looking at** — a command that names no tab lands on the tab that conversation has been working from (`tabs` marks it `your tab`), and never on the tab on screen. Switching tabs in the window is therefore safe: what you look at is yours to move, and it no longer pulls somebody else's work somewhere else. Naming a tab with `--tab <id>` — or `tab-select <id>` — is how a conversation moves its own.
- **A conversation only works in a tab it named — never in the one you happen to be looking at, and `tab-select <id>` is how it names one** — a command that names no tab acts on the tab that conversation has been working from. With none yet it used to adopt whatever tab you had in front, which handed your next click the decision of where an agent's command would land. That is gone: the command now says so and names the ways out, and `tabs` prints the same when it has no `your tab` line for it. **`tab-select <id>`** is new and is the plainest of them — it makes a tab the one that conversation works from and moves nothing on your screen (`--tab <id>` on a command at hand is that same act attached to a command; `tab-show <id>` remains the one that brings a tab up for you to look at). Closing the tab a conversation works from leaves it with no tab of its own rather than quietly handing it the next one — a cursor is written on a tab and ends with it — so it names one again; taking over a tab nobody owns is still allowed, now as something said rather than something inferred. A session spawned by another one is handed its tab as before (`tab-assign` from the parent, or `tab-new`).
- **There is no "open the browser" command any more — `navigate` is the first command, and it gives the conversation a tab of its own** — `navigate <url>` opens the workspace's window if it is not up (the tab that window is born with becomes the conversation's, so a fresh window is one tab, not two) and loads the url there; an existing window gets a new tab behind the person's, never a blank tab that was already there. With a tab of its own already, it is simply "go here". Every other command that acts on a page still refuses without a tab and names the ways out (`tab-select <id>`, `--tab <id>`, `tab-new <url>`). `tab-new` now **requires a url** — a tab exists to hold a page, and the tab a conversation needs first is what `navigate` gives it. Both name the tab they used in the reply (`Tab: <id>`), so a tab that was just created is findable without a `tabs` call. `open` existed for a window with no tab in it, which is not a state a conversation asks for; its one unique job — bringing a tab to the person — is now `tab-show`. And `tab-show` sets the window's shown tab **without raising the window**: taking over the person's screen and focus is not an automatic action's to do, so the conversation's reply is what tells them to look, and the app's browser strip is how they open it themselves.

- **`release` and `close` are gone — `tab-show` and `tab-close` are the whole window surface** — showing a tab and handing it over are one command with two modes: `tab-show <id>` makes a tab the one the window shows, without raising the window (your overlay and hold stay in place), while `tab-show <id> --handover` also drops them, so the page is the person's until your next command takes it back. Closing is `tab-close <id>`, as before, and the last tab takes the window with it. The window-level commands (`focus`, `hide`, `release`, `close`) were removed with them: there is nothing left to do to a window that is not about a tab.

- **A tab's task is inherited** — a tab a link or popup opens belongs to whatever the tab it came from belongs to, so a conversation's tabs are a **task group** rather than a list it happened to open: a link it could not follow itself still lands in its group. Who clicked is not asked — an agent's click and a person's look the same from here — because the tab it came from answers it. A tab opened from a tab nobody owns stays nobody's. Two consequences worth knowing: those tabs are listed under that conversation in the tab rail, and closing that conversation's tabs closes them too. `tabs` says `belongs to: …` for the same reason it no longer says "opened by": after inheritance, who *opened* it is not what the line means.

- **A tab in the background is a real tab — and only the one being worked on pretends to be in front** — a tab that was not on screen used to be parked at zero size: no viewport (coordinates in it meant nothing) and nothing painted (a screenshot of it came out empty). Tabs now keep the content area and are stacked under the one on screen, and the tab a conversation is working from is told it is in front, so a site cannot behave differently just because you switched tabs (measured: `hidden` and 2 frames in 2.5s before, `visible` at full frame rate after). Memory is the same either way — 613MB parked against 614MB for four tabs — so what this saves is CPU: the tabs nobody is working on stay throttled.

- **The agent works in its own tab, and your tab stays yours** — a command no longer comes to the front of the window to run: it acts on the tab that conversation works from, wherever that tab sits, and only `tab-show <id>` moves what you see (which is what it says). Opening a tab with `tab-new` opens it **behind** the one you are reading, so the window you are using is not taken away while a conversation works somewhere else in it — the tab is listed in the rail either way, and the agent's summary says which one it opened. It is the same rule at every level: a click, a screenshot and a console read all land on the conversation's tab. `tabs` still says which tab is yours (`your tab: …`), and `--tab <id>` names one for a single command without moving anything.

- **A project's three tiers are on its own page, and the prototype tier is gone** — the project detail page's **Goal, Specs & Plans** tab shows the work the folder holds: first the **goal** row, then the **index** row (`spec.md`), then **one row per piece of work**, each carrying a **Spec** and a **Plan** button that opens that tier's file — each labelled with its title and the file's own name beside it, since the file's name is what a link points at. **A tier that has not been written simply has no button**, rather than a warning or a count of what is missing. Underneath are the links that point at nothing, each with **Hand it to the conversation**, which puts the agent's own sentence into a conversation on this project's draft and sends nothing. It is read from the folder every time the tab is opened, so the page and the conversation can never disagree about what is there. **The prototype tier is gone with it**: `prototype_tool`, the per-prototype pages, panels, pickers and sidebar entries, a conversation's binding to a prototype, and the workspace-level list of prototypes have all been removed — a requirement's home is the project itself now, and no tool is needed to write one (the files are written with `Write`). Existing `prototypes/<slug>/` folders on disk are left exactly where they are: nothing migrates them, nothing reads them, and the app shows no entry for them. To keep a requirement, move its `*.spec.md` file into the project folder you want it in.

- **Tweaks have a home in the sidebar — and a switch** — a tweak used to be files an agent wrote with nothing in the app to show for them. There is now a **Tweaks** section: it opens a list of every tweak in the workspace — its name, the pages it is for, whether it has code, whether it is on — beside a page for the one you pick whose main business is **the switch**, with the line that says what it means: a tweak runs on the pages its match patterns name, and it is **off until you turn it on**, because naming those pages is not the same consent as agreeing to run the code in them. The page also lists the tweak's files (`tweak.css` / `tweak.js`) as paths with **Open folder** rather than an editor, the `@target` selectors it declares with when each last matched — separating *stopped matching, the page moved* from *never matched*, which is the one thing only that record can tell you — **Export**, which builds the loadable extension into a folder you pick, and **Delete** behind a confirmation. Nothing here creates a tweak: agents write them, and the empty state says so instead of offering a form. A tweak that is on still only runs in this app's own browser window; the exported extension is what carries it to the browser you actually work in.

- **A download in the browser window says so — and says where it went** — a download used to be answered with nothing at all: the file was written to your downloads folder and the window said not a word about it, so a click that worked looked exactly like a click that did nothing. It now appears as a **downloads button** in the window's toolbar — a spinner and the percentage while the file arrives — and opening it lists the recent downloads, each one a click that **shows the file in its folder**. The button carries the app's accent until that list has been looked at, so a download that finished while you were reading the page is still waiting to be noticed. The list belongs to the **workspace**, not to the window, and so does the record of where a file went: a download that is still arriving when you close the window keeps arriving, and the next window you open there is told where it landed. One thing changed about *where* a file lands, and it is now the same place for everyone: your downloads folder, whoever asked for it — a download is not a tab's, so nothing about it is filed under a conversation any more. A workspace that has downloaded nothing draws no button at all.

- **A design exports as an editable PowerPoint, not a picture of one** — the **Export…** menu gains **PPTX**, so a design can leave the app as a real `.pptx` whose text is text and whose boxes, borders and gradients are native PowerPoint shapes. It is built from the rendered design by the app's own hidden window (the vendored MIT `dom-to-pptx` engine), so no second browser is installed. A deck becomes **one slide per `<section class="slide">`, in order**, at the deck's own aspect; a plain design becomes a single slide holding the page. Two things to know before relying on it: the layout is rebuilt from measured geometry, so the text stays editable but will not reflow like a placeholder deck (retyping can overflow the box it was drawn in), and effects with no native PowerPoint equivalent — background/backdrop blur, blend modes, WebGL/canvas — are approximated or dropped. **PDF** and **PNG (one image per slide)** remain the exact-pixel options.

- **A web page can be a source — a bookmark with a guide** — a fourth kind of source, for when the thing worth keeping is a *page* rather than an integration. `type: "web"` with a `web.url` is the bookmark; `guide.md` says what the page is and how to work with it, and nothing is captured or copied into the source folder. The page is opened in the **workspace's browser window** when it is needed, so a page behind a login, or one a script builds after load, is available the way the person sees it. Everything else about a source comes for free: a web source is listed, @-mentionable, scoped for permissions and injected into each conversation's context like any other. Its detail page shows the address and the guide — there is no snapshot to refresh, and no server, so `source_test` has nothing to say about it. `browser_tool read --save <path>` is still there when a page is worth keeping as a file: it writes the page as markdown, keeps its images beside it, and the result can be read or edited later — an ordinary workspace file, not part of the source.

- **A design opens in a window of its own — from the design itself** — a design you keep reaching for can be opened as a mini-app of its own. The way in is the design's own menu: **Open in Its Own Window**, on the **⋯** menu of a design's page and on the right-click menu of a tile in the Designs list. It opens the design in **its own window** — no app interface, and no trace of the host around the design either: no header, no Present row, no frame, no rounded card. It fills the window edge to edge, **as if the page had been opened directly** (the only thing kept is the system title bar, which is what you drag the window by, and the window's own "nothing to show"/failure states, so a blank window never explains nothing). Opening it again **focuses the window already showing that design** rather than stacking a second one. **Press F11 (⌃⌘F on macOS) to take it fullscreen.** It is still a real, live render: approved actions, scheduled refreshes and pushed data all work exactly as they do in the app. It is a **temporary window**: closing it closes it (it never hides away), it is not restored on relaunch, it never stands in for the workspace's window, and it titles itself after the design. Nothing is pinned and there is no second list to keep in step — and the **tray no longer lists designs**: it brings windows back and holds the saved servers, while a design's window is opened from the design.

- **`browser_tool read --save` keeps a page as a file you can work with** — reading a page as an article does not have to end in the reply: `read --save <path>` writes the note to a file and hands back only a summary, so a long page is not shipped through the conversation again. The file is an ordinary workspace file — `Read`/`Edit` work on it, and its YAML frontmatter and markdown body can be handled separately. Images are **opt-in**: `read --save <path> --images` also brings down every image the article references into `<note>.assets/` beside the note and rewrites the note's links to those relative paths. Without `--images`, `--save` writes only the note and says how many images were left as links. Images are fetched through the page first, then through the window's session when the browser refuses a cross-origin read; an image that cannot be fetched keeps its remote url and the reply says why. Ceilings: 100 images, 8 MB each, 100 MB total. Plain `read` writes nothing and downloads nothing.

- **A window can connect to a hub — the app does not become one thing or the other** — a machine that runs Server Mode is a hub, and any desktop client can now open a **remote window** on it without setting `CRAFT_SERVER_URL` in a terminal. **Connect to Server…**, in the app menu, keeps a list of servers: it takes a new server's WebSocket URL and token (with a **Test Connection** that lists the workspaces it finds), and **Open** opens a window whose sessions, tools and browser run on that server — connecting is an action, the way VS Code treats a remote connection, not a settings page. Several servers coexist; the star marks the one new windows (and launch, with nothing to restore) open on, and the **tray** lists them all. Other windows stay on this machine. Connection is a property of the **window**, the way VS Code treats a Remote-SSH window: local and remote windows sit side by side, **Server Mode keeps running** while a window is connected elsewhere, and switching workspace inside a remote window **re-opens that workspace in the same window** — the window and its hub stay, the way a remote folder is re-opened in VS Code — while "open in new window" still gives the workspace a window of its own. Nothing waits for a restart. While a window is connected to a hub, **Settings → Server** says the server belongs to that host instead of silently editing it. The hub's **Settings → Server** lists the **devices** it can drive — one row per machine, with the platform and whether it can host browser tools. Its own machine is not on the list: there the agent's shell, files and browser are simply the default. A machine can be driven by several servers at once, and a workspace id is only unique on the server that issued it — so each server's browser windows are filed under that saved connection. Two hubs that both call their workspace `ws-1` get two windows, and neither window's tab strip lists the other's tabs. And the hub's agent drives the **connected client's** browser through the same `client:browser:invoke` bridge remote workspaces already used.

- **Every connected device is a tool the agent can name** — with several clients connected to one hub, "which machine does this run on?" is answered explicitly instead of by the device that sent the last message. The agent gets one `device_tool`: `devices` lists what is connected and what each one allows, and any other command — `bash`, `read`/`write`/`edit`, `list`/`stat`, `glob`/`grep`, `browser` — takes `device` and runs there. A device that is named is the device that runs it: an unknown name, a device without that capability, or a disconnected device is an error, never a quiet fallback to this machine. Shell and file access on another device stay inside that device's own working directory, and a remote client's work is rooted in a per-hub folder — `~/.craft-agent/.hub/<hub device id>/<workspace id>`, created on demand — so two hubs and two workspaces cannot write over each other. The hub's own machine is not on the list: it is where the agent already runs, so its shell, files and browser are simply the default tools.

- **A device stays reachable with no window open** — saving a server in **Connect to Server…** is what makes this machine a device for it, and it does so **once per server**: the app keeps one connection per saved server, carrying shell, file and browser access, so any of those hubs can drive this machine while every window is closed. They belong to the app rather than to a window, so a call never lands on a window that is closing, and `device_tool` keeps naming one device however many windows are open. The hub lists that machine **once** in **Settings → Server**, however many windows are open.

- **A device's folders are chosen on that device** — a server driving this machine used to be confined to `~/.craft-agent/.hub/<hub device id>/<workspace id>`, so its agent started in a working directory that belonged to neither side and could reach nothing this machine actually works in. Saving a server with device access now also lets that saved connection carry a list of **authorized folders**; the edit form offers this machine's workspaces as one-click shortcuts, but a workspace is only reachable once it is in that list. `device_tool` is path-based and independent of the hub's workspaces: `devices` reports exactly those folders, a command's `cwd` must be inside one of them, and a path outside the list is refused. Folders are stored per saved server and survive a rename or token rotation; an edit that does not mention them keeps them.

## Improvements

- **A workspace is no longer a door to another server** — workspaces used to be able to record a server of their own, which made "remote" a property of a workspace and left each window translating one workspace id into another. Remote work is now a window on a saved server (**Connect to Server…**): a workspace belongs to the server that owns it, the client's servers are an app-level list, and nothing translates workspace ids. An install that had remote workspaces gets them folded into that list on first launch (one entry per URL) and removed from the local workspace list.

- **Design exports work from a browser and from a remote window** — an export used to ask the *calling* client for a destination path and then write it on the hub, which only held together when both were the same machine: a webui export failed outright, and a remote window's save dialog named a path that did not exist on the hub. Now the hub renders into a short-lived export file and hands back an id: the browser downloads it over the same authenticated HTTP port, and a remote window streams it to a path the person picks locally. Per-slide PNGs arrive as one zip. PDF/PNG/video/PPTX still need the desktop renderer on the hub; HTML and ZIP work anywhere.

- **A diagram that arrives as an SVG is no longer a dead end** — `drawio_tool` now reads a diagram file through the wrapper an exported SVG carries, so every command takes one: `pages` lists the copy's pages, `render` draws it, and `export <file>.svg --to <file>.drawio --format drawio` writes the document back out — as a file to edit with `Write`/`Edit` and export again. That unwrap was already how `pages` worked; it is now what reading a diagram file *means*, so a command is handed the document whether the file on disk is an `<mxfile>` or an editable SVG, and "can this be read back" stops resting on drawio's own load path.

- **A diagram in a conversation is clicked for the full size, and dragged to pan — and the two are one gesture** — they used to be two different diagrams: a mermaid one opened the full-screen window on a click and could not be dragged at all, and a drawio one could be dragged but answered a click with nothing. Both now do both, reading the same gesture the same way: dragging moves what you are looking at, and a press that stayed put opens the window — with a few pixels of slack, so a hand that shakes while pressing is still a click rather than a pan that nudged the drawing. The drawio block gains the entry it was missing: its window was reachable only from the button in the corner, which is still there. Reset-by-double-click stays where a click has nothing else to do — the full-screen window — since a block's first click is spent opening it.

- **A diagram is panned, not scrolled — and it goes wherever you put it** — a diagram used to live in a scrolling box, which pinned its edges to the border of that box: the corner of a big diagram could not be read without hugging the edge, no gesture brought one inward, and a scrollbar was always there to explain the limits. The **full-screen window** pans by a **transform** now, as mermaid's window and the image preview do: the drawing can be pulled anywhere at all — an edge clear across to the other side, a corner moved off a border — and there is neither a scroll range to run out of nor a scrollbar. One rule went away with it: a drawing only a little too wide used to be shrunk to fit so as not to need a scrollbar, and the window now shows it at its own size like every other. What you see on opening is unchanged (100% is the size it was authored at, centred), and the zoom arithmetic is the one the other previews already use, so the wheel holds the point under the pointer here exactly as it does there. A diagram **in a conversation** is not this: it is the box mermaid's is, and stays one — as big as it was drawn, a scrollbar when it does not fit, dragged to be moved along, and a click to open the window.

- **A markdown file is read as a document and edited as its source** — the three places a `.md` is shown are one component: the `markdown-preview` block inside a conversation, the full-screen window a `.md` link opens, and a row on the project page's **Goal, Specs & Plans** tab. **Reading draws the document**: the same renderer the conversation draws messages with, so a `.md` that quotes a diagram, a page, a table or a diff shows those things as themselves — and a document that names another document stops at one level, because drawing that one inside this one has no floor. **Editing is the source**: the file as text, with markdown highlighting, and what reaches the disk is exactly the characters on screen — nothing is parsed and written back out on the way, so a construct the app has no node for cannot be quietly dropped from somebody's file, which is what any rich editor risks every time it parses a document it then saves. The block in a conversation only ever reads — a fixed-height look at the document with a fade at the bottom — and its corner carries **two ways into the window**: the pencil opens it **on the source**, with the caret already in the text, and the four corners open it to **read** in, in the same corner and with the same meaning that button has on a diagram, a page and a mermaid block. Inside the window a pencil in its own header switches between the two faces, and a change reaches the same file about a second after you stop typing, including the one still pending when you close the window — bounded by the same rule that let the app show you the file in the first place (it is the same file editor the diagram and the page use underneath). A link in the rendered document opens in the app like any other link here.

- **A project page says what the folder has wrong with it, not only the agent** — the same facts the agent gets are now on the project page's **Goal, Specs & Plans** tab: the links that point at nothing are spelled out under the list of work, one line per thing, each in your language with the sentence the agent prints underneath, and each with **Hand it to the conversation**, which puts that sentence into the conversation's draft and sends nothing, so you say what you want done with it. They appear **only when there is something to say**: a folder with nothing broken says nothing, because "ready to hand over" is a verdict nobody opened the page to hear. Those facts are said **once**: the report's `issues:` and the page's other warning box carry what could not be read as written — a picture that no longer matches its diagram — and do not repeat what the gate already names.

- **A brief's picture is checked against the diagram it was drawn from** — a brief shows a diagram as an ordinary markdown picture (`![The cart](cart.drawio.svg)`), and that picture is a **snapshot**: editing the `.drawio` beside it changes nothing until the export is run again, which the guide itself calls the one way this pair goes wrong. Nothing could see the pair, because nothing tied a picture to a source. The report does now, and it does not go by a timestamp: an exported SVG carries **its own copy of the document it was drawn from**, so the two documents are compared. What is compared is what the drawing *says* — which cell, saying what, styled how, where — read by attribute name, because the picture is the drawing as drawio wrote it and the file is the drawing as you typed it: whitespace, attribute order and every attribute drawio fills in for itself are not differences. A difference is reported only when it is certain, as one line in the issues the page shows: *"cart.drawio.svg is not what cart.drawio draws any more — it was exported before the diagram changed."* A picture with no `.drawio` of that name beside it is passed over in silence, and so is one exported without its copy (`svg` rather than `svg --editable` — a picture and no document to compare). One change is deliberately not reported: a page *added* to the `.drawio` looks exactly like an export made with `--page`, so adding a page is a reason to export again even though nothing complains.

- **The Windows title bar is the app's own** — the window used to keep Windows' native title bar, with the app's header sitting under it as a second strip. The bar is now drawn by the app the way macOS's already is: the TopBar *is* the title bar, dragged by itself, and the row continues straight to the window's edge instead of starting below a system strip. The minimize/maximize/close buttons are still Windows' own, painted over the bar's right end — so Snap Layouts (hover the maximize button for a layout), double-click-to-maximize, and every other native caption behaviour are unchanged, and the app's own top-right controls step left of that strip to stay clickable. The Mica/Acrylic backdrop is kept: the caption strip is transparent, so the material shows through it and the glass runs from the very top of the window, and the button glyphs follow the system's light/dark setting. A design opened in its own window is deliberately not this — it keeps the standard title bar, since it has no in-app header and that bar is what it is dragged by.

- **The browser window gets its own taskbar button — and it is not offered as something to pin** — the workspace's browser window used to fold into the app's taskbar button, because every window in a process shares one App User Model ID. It now carries its own: the window is a taskbar entry of its own, named **Craft Browser** and wearing a blue version of the Craft mark (the app's own stays purple, so the two are told apart at a glance). Its menu is left with **Close window**: a window that is a place to look at is not an app to launch, and Windows' **Pin to taskbar** entry — which it lists for any window that has a taskbar button — is dropped by setting the `AppUserModel.PreventPinning` window property. Electron does not expose that property (its `setAppDetails` covers only the app id and the relaunch fields), so the app sets it through the Win32 `IPropertyStore` instead, just before it gives the window its id. It is Windows-only, where the concept exists, and nothing about it is load-bearing: where it fails the window simply behaves as it did before. macOS ignores a window's icon and draws the app's, as it always has.

## Bug Fixes

- **A picture named beside a document is drawn** — a markdown file that referred to a picture in its own folder (`![](shots/cart.png)`) showed a broken image: the destination reached the browser as an `<img src>`, which is resolved against the app's own origin rather than against the folder the document is in, so it never reached the file — and an absolute path was stripped before it got that far, leaving no way at all to put a picture beside a document. A relative destination is now read from the document's own folder and shown as a data URL: in a document opened full size, in a `markdown-preview` block, and in a project's `spec.md` on its page — which is where a brief's own pictures live. An `http(s)`/`data` destination is untouched, and an absolute path is not "beside the document", so it is left exactly as it was. The picture is only ever an `<img>`, which is the point: an SVG shown this way is drawn in the browser's static image mode, so nothing in it runs and nothing in it is fetched. And the read goes through the same boundary every other read does — a `../` escape is refused by it rather than by this.

- **An HTML preview is a window, and a wide page can be reached** — the full-screen preview used to size its frame to the content's height, so the whole page lay out and the overlay scrolled instead of the page. The vertical half worked; the horizontal half had nothing to scroll with — a page wider than the box was simply cut off, and the page's own overflow was switched off while the size was being measured, so not even the page could scroll it back. The frame is now the size of the box it is given and the page scrolls inside it, both ways, as it would in a browser window — the same thing the in-conversation block already draws. That also settles what happened when you opened the editor: the page's height used to change the moment you did, because the editor needs a viewport it can put its controls above, and now the two modes share one box (the controls sit in a single fixed-height row, so nothing shifts when a notice appears either). One consequence worth knowing: a page shorter than the box now shows white below it rather than shrinking the box to fit.

- **A big diagram is drawn at the size it was authored, not at the size the viewer's own box made it** — a diagram wider than about a thousand pixels came out shrunken, its words too small to read, while the same file opened at its own size in drawio. The viewer that draws a diagram for the app **fits a diagram to the box it is drawing in** when it does not fit, and that box is the app's own drawing engine: kept off-screen, a thousand pixels wide, and nothing to do with how big a diagram is wanted. What came back was therefore the fitted drawing — and the size the app reads off it is fitted the same way, because the viewer works that number out at the scale it drew at — so 100% *was* the shrunken size, labels included. The viewer is now told not to fit, which is the one switch that rule hangs on. Measured on a 2218-pixel-wide document: 1030 wide and `scale(0.46)` before, 2218 wide and `scale(1)` after.

- **A diagram's zoom does what the number says** — zooming a drawio diagram moved the percentage while the drawing stayed exactly the same size: the wrong one of them was being resized. The viewer hands the app an SVG with no `viewBox`, so there was no size to read out of it, and a size written back onto it was a size nothing drew by. The size the markup does state is now read off it — the `min-width`/`min-height` the viewer writes, which are the drawing's own bounds — and the drawing is pinned to that size while the zoom is a transform on it, so 100% is the size it was drawn at and "fit" fits. That is the full-screen window, which is where a diagram is zoomed. One side effect worth expecting: the wheel now steps the way every other preview's zoom steps (a mouse notch is a notch, a trackpad pinch is a pinch) instead of halving the drawing per notch.

- **drawio is in the app's language, not English** — the diagram editor and the viewer behind a diagram were English whatever the app was set to, because nothing ever told them and the one way drawio works it out for itself is limited to its own hostnames. The language now travels in the address each frame is opened with — where both of them read it, and the only place that works: each decides as it loads, before anything here could speak to it — translated on the way into the names drawio uses, where this app's `zh-Hans` is plain `zh`. A window that is already open keeps the language it opened in; opening it again takes the change.

- **A mermaid diagram's wheel zooms in the full-screen window** — the zoom buttons worked and the wheel did nothing, and the reason was a box that did not exist yet: the window's contents are mounted one commit after it opens, so the wheel was being attached while there was nothing to attach it to — and a listener set up that way never gets another chance. It is now attached the moment the box appears, so a wheel zooms about the pointer the way the buttons zoom about the middle. The same fault was in the image window's wheel, which shares this machinery.

- **A press that moved is a drag, even where there is nothing to drag** — on a diagram small enough to fit its box, a drag was read as a click and opened the full-screen window, which is exactly what a hand moving across a picture is not asking for. The gesture is now read the same way on every diagram, large or small: what separates a click from a drag is a few pixels of travel, not whether there was anything to pan.

- **A link that opened a bare window now opens a tab** — a `target="_blank"` link on a page we serve, an OAuth popup, a link out to a real site: each used to open an Electron window with no toolbar, which for a page we serve looked like somebody else's site. All of them are **tabs of the same window** now, and nothing opens a second window any more.

- **"New tab" adds a tab, and the window comes up on it** — a window that is already open now gets a real new tab, brought to the front, where before a window holding one untouched blank tab read as "not opened yet": the request was answered by that tab, which had nothing to load, so the click did nothing at all. A window that is not up yet still opens into its own blank tab, so a fresh window never comes up with two of them. The window's tab list under its badge in the top bar now lists whatever the window holds, **including a single tab** — it used to keep quiet about a one-tab window, which is exactly when you want to know what is open — and "New tab" sits with the window's other actions rather than inside the list, so it is there either way. An entry in that list shows its tab and brings the window up with it, so a window that is behind something else is reached from the top bar.

- **A new tab no longer shows the tab that was there before** — a tab that is made and left with nothing in it draws no pixels of its own, and the window's tabs all sit in the same place, so switching to it showed whatever was underneath: a tab opened from the top bar, and a `tab-new` from a conversation, both left you looking at the tab you were already on. Every tab is now given the "New Tab" page the moment it is made, whichever way it was opened. A tab that is closed now leaves the window as well: its view used to stay behind — still drawing at the content area, and still costing a renderer for a tab nobody could name.

- **The "system prompt context changed" note now says what changed, and gives the way out that fits it** — a session pins its system prompt on its first turn (your preferences, the commit co-author setting, and the bound project's block), because that text is the cached prefix; a change made underneath it is therefore reported rather than silently applied. The report was one sentence for three different drifts — *"Start a new session to apply preference or project-memory changes"* — and for the project's own material that advice is wrong: MEMORY.md and the list of reference files are **files**, which the session can simply re-read, so being told to start a new session traded a whole conversation for a read. Those notices now name the path and say what is stale ("Read …MEMORY.md for the newest notes"), while a changed preference or co-author setting still asks for a new session — a session cannot re-read instructions into a prompt it has already sent. The project's block is compared part by part as well, so an edit to the memory and a new reference file are two different lines instead of one vague one, and each kind of drift is reported once.

- **A Windows taskbar badge that would not go away now goes away** — the unread number on the Windows taskbar icon is drawn in the renderer and then handed back to the main process to be applied, and the count can change — and be cleared to zero — in the time that round trip takes. A draw that arrived after the clear put the old number back, and nothing ever removed it again: the count it would have to change from was already zero, so no further clear followed, and the badge sat there until the app was restarted. A badge is now applied only if it is for the count that is still current, so a late draw from a count that has since moved on is dropped. The overlay is also applied to every window rather than only the first one — clearing already touched them all — so the number lands on the window you are actually looking at.

- **A packaged build now ships the diagram editor** — the drawio webapp a diagram is drawn and edited by lives in `resources/drawio/`, and it is not committed: it is fetched and pruned by `scripts/fetch-drawio-assets.ts`. Nothing in the packaging path ever ran that script, so a release copied a `resources/` without it and the app — finding no bundle at its own path — reported the editor as not installed and drew no diagram, on macOS, Windows and Linux alike. Every packaging entry point now fetches it before the build (`electron:dist*`, `build-dmg.sh`, `build-linux.sh`, `build-win.ps1`), so an installed app has the editor it advertises. The fetch also retries a transient failure per file and resumes what it already fetched instead of restarting: it now sits on the path where one socket reset would otherwise fail a whole release.
