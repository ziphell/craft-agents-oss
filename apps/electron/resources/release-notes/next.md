# Pending Release Notes

This file accumulates release notes for the next unreleased version. PRs that add user-visible behavior should append a bullet to the relevant section here. Versioned files (`X.Y.Z.md`) are owned by the release skill — never create them in feature commits.

## Features

- **Element picker for browser_tool** — new `pick` command: the agent asks you to click an element on the page and gets back a stable selector (`data-testid` → `id` → `:nth-of-type` path) plus tag, text and viewport rect. Cancel with Escape or `--timeout <ms>`. Runs through the existing CDP session, so it needs no permission changes and stays sandboxed.
- **Prototype patches that survive a reload** — new `prototype-apply <slug>` / `prototype-clear <slug>` commands replay a prototype's patch files (`{workspace}/prototypes/{slug}/patches/{lane}-{nnn}-{name}.{css|js}`) into the browser. The patch index is recomputed from disk each time, so editing or deleting a patch file and re-running the command is enough. Patches are applied to the current page and registered for every future document, so a reload keeps them. Requires the patches directory to be writable in the current permission mode (`prototypesFolderPath` is now an Explore-mode write target).
- **Prototype export** — new `prototype-export <slug>` command builds the deliverable into `prototypes/{slug}/dist/extension/`: a loadable Chrome extension (load it unpacked from `chrome://extensions`; nothing is published to a store) that applies the patches to the live pages it covers and ships the prototype's own documents. The contract's `x-mock` responses travel with it, so a prototype built against the mock layer still works once handed over, and `README.md` says where it applies, which requests are faked and which build it is. `dist/dev-spec.md` still lists every patch in replay order, now grouped by page.
- **API contracts as a first-class deliverable** — new `prototype-contract-compose <slug>` / `prototype-contract-export <slug>` commands. Contract fragments under `prototypes/{slug}/services/{svc}/paths/*.yaml` are the source of truth (alongside `fixtures/*.json`); compose merges them into one `openapi.yaml` (reporting duplicate paths and `x-mock` fixtures that don't exist), and export writes the backend handoff into `dist/`: `openapi.yaml`, `contract.md` and `fixtures/`. `contract.md` lists endpoints and declared error responses, and explicitly flags what is *not* declared (no error responses, no `authType`, no pagination/idempotency/concurrency notes) so an incomplete handoff is visible instead of silent. No new dependencies.
- **Contract-driven network mocking** — new `prototype-mock-apply <slug>` / `prototype-mock-clear` commands serve the contract's `x-mock` responses through CDP `Fetch` interception, so the prototype runs before the backend exists. Interception happens in the browser's network layer: `fetch` and `XMLHttpRequest` (axios) are both covered, the app needs no mock-server URL, and fulfilled responses carry CORS headers. Endpoints without `x-mock` pass through; routes whose fixture file is missing are skipped and reported rather than served empty. No new dependencies.
- **Multi-page prototypes** — a flow is more than one screen. A prototype declares its other pages (`prototype-pages --add payment=https://app.example.com/pay` for one that belongs to a real site, `--rename`, `--remove`), and `prototype-export` scopes the delivered extension to **all** of them — one match pattern per live page, so a screen left out is an error rather than a page that quietly gets no patches. `prototype-status` lists the pages in flow order, `prototype-open --page <name>` opens one, and `snapshot` says which page a window is on. A page of ours is its own document (a top-level `.html` is a page), and every one of them ships in the extension under its own name — so the links an author wrote between pages keep working instead of 404ing in the package. (See "A prototype is a flow of pages" below: a page's kind replaced the prototype's.)
- **Prototype addresses are stable across restarts** — a prototype's page is served at `http://<slug>-<hash>.localhost/` (no port), answered by an `http` handler Electron registers on the browser session, instead of a loopback listener whose port changed on every launch. Anything that is not one of those hosts — real sites, local dev servers on `*.localhost`: everything — is passed straight through to Chromium's network stack unchanged. Because the origin no longer moves, a scratch prototype keeps its cookies and `localStorage` between runs.
- **`prototype-status <slug>` and artifact ownership checks** — a read-only report of a prototype: the pages it has and anything wrong with them, patches by lane (and how many are scoped to one page), per-service endpoint/mock/fragment/fixture counts, `dist/` contents, and ownership violations. Ownership makes parallel work safe by giving every artifact path exactly one writer (lanes write `patches/{lane}-…`, `services/*/paths/`, `services/*/fixtures/`; the page documents, `config.json`, `services/*/openapi.yaml` and `dist/` belong to the control plane). The check surfaces three things that were previously silent: patches with an undeclared lane prefix, misnamed patch files the replay scanner ignores, and paths nobody owns.
- **`prototype-open <slug>`** — opens a prototype in the browser: a live page goes to its own address with the patches replayed into it, and a page of ours goes to the prototype's own origin, rendered from that document with the patches it carries; with no entry page marked, it opens the page index. `--page <name>` opens a named page, and without it the open starts from the page the window is already on, then the entry page, then the index. Fails with the remedy named when there is nothing to open. Starting a prototype from nothing needs no special command — write `prototypes/{slug}/cart.html`, then open it.
- **A prototype is a flow of pages** — the `kind` moved from the prototype to the **page**, so a prototype is a table of pages and one flow can mix both: a page of ours (a document we own, `<name>.html` in the prototype) and a live page (someone else's address, patched in place). This replaces the per-prototype `kind` above. The sidebar lists a prototype's pages under it — click one to open it, mark one as the entry, rename or remove it — and the New Prototype dialog asks for a name only, with kind and address asked for when a page is added. `/` opens the **entry page** you marked, or a generated **page index** of every page when you have not marked one (with `/_index` always showing that index). Patches can be scoped to one page by directory (`patches/<page>/…`; `patches/*` still applies to every page), `prototype-apply` replays the patches of the page the window is on and says which page that was, and one export covers the whole flow: our pages ship under their own file names, each live page gets its own content script, the generated page index is the extension's options page, and the toolbar icon opens the entry page. Existing prototypes need no migration — old configs are read as a page table.

- **Requirements in the prototype workspace** — a prototype now carries a `prd.md` whose entries are headed by a stable id (`## R-001 …`), and any patch header or page document declares what it serves with `@requirement R-001`. `prototype-status` turns those markers into the two answers nobody can get by reading files one at a time: a requirement nothing implements, and a marker naming an id the PRD does not define. `dist/dev-spec.md` carries the same table to whoever receives the delivery, and names the changes that claim no requirement at all.
- **Research findings as files** — one finding per file under `prototypes/<slug>/research/` (`# F-001 …` plus `claim:`, `source:`, `captured:`, `evidence:`, `requirements:` lines). Evidence is checked against the disk, a finding with no `claim:` is reported, and neither findings nor frames are packaged: the reader receives the requirements, not the author's notes. A bound session's context now lists the requirements with what refers to each, and the findings recorded so far.
- **Frame capture instead of screen recording** — new `prototype-record start` / `prototype-record stop [slug]` commands keep frames of the browser window and write them under `research/frames/<session>/`. Two samplers, because a screen changes for two reasons: the screen is compared every 400 ms and a frame is kept when more than 0.5% of it changed (a streaming answer, a list filling in), and every action taken on the page — click, typing, key, navigation — is kept whatever the screen did, plus a second frame a moment later for what it produced. Frames are numbered JPEGs with a `frames.json` index and an `index.md` table, each carrying its address, its page and why it is there, so a finding can cite one. Caps at 60 frames per capture (`--max`, `--interval`, `--threshold`), and says so when it hit the ceiling instead of quietly dropping the difference.

- **Import a recording, get frames** — `prototype-record import <path>` samples a video you recorded elsewhere (a phone, Loom, QuickTime) into the same `research/frames/<session>/` a live capture writes: numbered JPEGs, a `frames.json` index and an `index.md` table where each frame carries its position in the recording (`imported [0:12.4]`). `--every 2s` sets the interval, `--changes` keeps only the moments that moved, `--max 40` caps the frames and reports when it hit the ceiling. The recording is copied into `research/videos/` so the capture can be re-sampled later, and decoding is Chromium's — no ffmpeg — so a codec it cannot read (HEVC/H.265, ProRes, some `.mov`) fails with a message that says so. The prototype page's Frames section has the same thing behind an "Import a recording" button, with the file picker running in the main process.

- **Acceptance checks that run** — a requirement in `prd.md` can carry `check:` lines (`check: selector [data-cart-total]`, `check: endpoint GET /api/cart`), and `prototype-verify` answers them: the selector against the page this session's window is on, the endpoint against the contract. With no page open the page checks report **skipped** rather than failed, and an unsupported kind is refused when the PRD is parsed instead of looking like a check that passed. The run writes `dist/acceptance.md` beside the change spec, and changes nothing else.
- **A prototype can say which project it was made for** — `prototype-project <slug>` records one edge in the prototype's config (`--clear` removes it). Not a container: the prototype stays where it is, nothing moves in or out, and the bound session's context now says which side a new file belongs on. A project deleted while a prototype still names it is reported rather than left showing a name that no longer resolves.
- **A project's conversations pick up its prototype** — the project detail page lists the prototypes that were made for it (a **Prototypes** tab, with add and remove), and a prototype's own page has the matching row to set or clear its project — the same edge `prototype-project` writes, now reachable without an agent turn. When exactly one prototype belongs to a project, every conversation in that project works on it **without being bound one at a time**: the window's address bar and its prototype actions, the agent's default slug for `prototype-*` commands, and the prototype context in the prompt all resolve it the same way, live — so a conversation created before the project had a prototype benefits too, and moving the project to another prototype moves its conversations with it. A conversation's own binding still wins, and clearing it falls back to the project's rather than to nothing (the header's prototype menu shows which of the two is in effect). With no prototype there is nothing to inherit; with several the project names no single prototype, so nothing is assumed and both the project tab and that menu say so instead. A conversation that was already running when its prototype changed says so on its next message: the system prompt is pinned at the session's first turn (the SDK expects a session's prompt to stay put), so rather than let the agent keep working from a paragraph that describes the wrong prototype, it reports the change and points at a new session.

- **"Add to conversation" from the element picker** — the pick button now turns selection **on and leaves it on**. Click it once and every click on the page adds that element to the conversation as a **chip** in the composer; move to another page of the window and keep picking — any page's elements can be added, and each one carries the page it came from. It ends when you say so: Escape in the page, or the button again (the button shows the mode the window is actually in, so an Escape is reflected there too). Picking appends: a draft you were writing survives, and the chip shows what the element says, with its selector and its page on hover. When you send the message the chip is rewritten into a readable reference that says which page it was picked on, so what the model reads is a sentence rather than an internal marker — and a message with no text but a chip still sends. It needs no prototype and no bound conversation: the element goes to the conversation you are looking at, and if this workspace has none, one is opened for it. The prototype's own edit flow is unchanged apart from its prompt now going in above your draft instead of overwriting it.

- **A patch can now say what it is aimed at** — a patch header may carry `@target <css selector>` (alongside the existing `@requirement R-001`), and `prototype-apply` counts what each declared selector matched. It reports the two facts that used to be indistinguishable from "the change did nothing": a selector that **matched nothing and never has** (wrong selector, or the wrong page), and one that **matched before and does not now** — the page moved — with selectors that resolve to a single element on the page today, so a drifted patch is re-anchorable rather than only reportable. Each successful match is recorded under `prototypes/<slug>/anchors/`, which is what makes the second answer possible: the record keeps what the element looked like and when it last matched, so "it stopped matching" can be told from "it never did". The prototype page lists every patch with its page and targets, plus an **Anchors** section showing each one's state; patches with no `@target` are named in the output as unchecked rather than reported as a clean run.

- **Edits show up in the open window without clicking apply** — saving a file under `patches/` or `assets/`, or changing a page document, replays that prototype into every window showing it: a page of ours reloads (the host re-renders from disk), someone else's live page is re-patched. Multi-file saves are coalesced into one replay, and the switch is in the prototype page's Patches section — on by default, because "I saved the patch and nothing happened" is the failure this removes, and off when a window holds something you would lose (replaying a live page reloads it).

- **`prototype-commit` folds a prototype's change layer into what owns it** — the inverse of appending yet another patch: on a page of ours the CSS is folded into `assets/<page>/committed.css` and the scripts are promoted into `assets/<page>/committed.js`, both referenced from the document; on a live page (whose address we can never rewrite) everything is folded into `patches/<page>/Z-001-upper.css` / `Z-002-upper.js`, which replay after every other patch by rule. Each folded change leaves a provenance header naming where it came from and carrying its `@target`/`@requirement` markers, so the anchors and the requirement thread survive the fold; the patch files that were folded are then deleted. It is the one prototype action with no undo — the panel asks first, and your own git is where the before and after live — so it is meant for the moment the work has stopped moving. `--page <name>` folds one page's own patches and leaves the shared ones alone.

- **A window holds more than one page** — opening a prototype no longer replaces what the window was showing: `prototype-open`, the prototype page's Open button and a prototype address typed into the address bar each open a **page of their own**, so two prototypes can be worked on side by side instead of one at a time. Every window has a **page rail down its left edge**, running the full height of the window with the address bar to its right — the back button and the address start where the pages end. It holds one row per page with its title, the page on screen raised, a close button on each, and a `+` for a new one — always, including with a single page, because that `+` is how you open something yourself; the pages are the topmost thing in the window, so nothing covers them. It is a column and not a row across the top on purpose: pages are a list that grows with use, and a row has to share its width with the address bar — a second page scrolled the bar aside and pushed the pages after it out of sight. The chrome's colours are the app's throughout: a page that paints itself dark no longer repaints the address bar and the rail beside it (the window's own chip in the top bar still takes the page's colour, which is about *which* window it is). The window's badge in the top bar lists the same pages under it (marked with a count), so a window that is not in front can still be switched page by page. `tabs` lists them for the agent, `tab-new [url]` adds one, `tab-close <id>` closes one (closing the last closes the window), and any command can name the page it acts on with `--tab <id>` — the window brings that page forward while the command runs, so which prototype is being worked on is never implied. A window that has just been created is opened *into* rather than beside: its own blank page is what a window is made of, so a freshly opened prototype is one page, not two.
- **The browser is one window per workspace** — every conversation in a workspace, and you, now share a single browser window, with each page of it a **tab** instead of a window of its own. Ask two conversations to look at two different prototypes and they end up side by side in the same window rather than in two windows; open a page by hand and it lands in that same window. It is not a prototype thing: the same window is where a general task's browsing happens. `browserPane` resolves the workspace's window for everyone, so "which window is mine" stopped being a question — a window now carries only *who is driving it at the moment* (a lease, renewed by every command and released when a turn ends). Two things follow: `windows` reports a window's `driver` instead of a `lockState` (it is shared, so a lease is not a lock), and `close` on that window means "close the pages you opened" rather than closing it — which is what "don't close the user's things" means once the window is everyone's. Workspaces stay apart: each has its own window.
- **Opening a browser opens a page** — the top bar's "New Browser Window" is now "New page", since there is only one window to put it in. A page the agent opened in this window is marked with a small icon in the page rail.
- **Which prototype a page is for now comes from the page** — with a window holding several prototypes' pages at once, `snapshot` and `windows` name the prototype of the page **on screen** (recorded when it was opened, which is the only fact that survives an overlay loading a third-party site) instead of the conversation's binding, which is now only the fallback for a page that belongs to none. `prototype-*` commands with no slug mean "the prototype of the page in front of you", so one conversation can drive several prototypes without declaring any of them: `--tab <id>` picks the page, the page says whose it is. Existing behaviour is unchanged for a single-prototype conversation.
- **Each page says what it is, who asked for it and who is driving it** — `tabs` prints, per page, what the page itself reports (its real address, its title, whether it is loading, which prototype it is for and which page of that prototype it is on) and, separately, what is stated about it: `opened by: agent (session-…)` or `opened by: a person`, and `driven by: <session>` or `nobody right now`. The three are kept apart on purpose — one is measured, one is intent, one is a lease (who is working on this page at the moment, released when their turn ends) — and the first two are what let a conversation tell its own pages from everybody else's. Pages the agent opened are marked with a small icon in the window's page rail, and a page some conversation is working on right now gets a dot.
- **A conversation can only work on — and close — what is its own** — the page-level half of "don't touch other people's things". A page is yours to work on when it belongs to no prototype (an ordinary page: anybody's, which is what "you open it, the agent takes over" means for a page that has nothing to do with prototypes), when it is for the prototype this conversation works on, or when this conversation opened it. Another conversation's prototype is refused, and the refusal names it and says how to bind it. Closing is narrower still: only pages **this conversation opened** — the user's pages and another conversation's are not yours to close however convenient it would be. `close` on the shared window therefore stopped being a flat refusal: it closes the pages you opened (leaving a fresh page if they were all of them) and says so, while the window itself stays — it belongs to the workspace.
- **A link that wants its own window opens a page beside the one that asked** — `target="_blank"`, `window.open`, popups and a prototype's own links all become **pages of the same window**, inserted right after the page they came from, instead of bare Electron windows with no toolbar, no prototype and no patches. Which kind it was is recorded per page (`opened as: a popup (no window.opener here)` / `a link that wanted its own window` in `tabs`), because there is one cost worth being able to name: a page opened this way has no `window.opener`, so a popup waiting for a `postMessage` from the page that opened it — Google's sign-in is the usual example — will wait forever. Such a page also cannot close itself (Chromium only lets scripts close windows that scripts opened), so it stays in the page rail until you or the agent closes it. A `background-tab` request is added without coming to the front.

## Improvements

- **`prototype-status` lists what each patch is aimed at**, and reports anchor records that outlived the patch that declared them — a record nothing refers to any more is named rather than left looking checked.

## Bug Fixes

- **A link that opened a bare window now opens a page** — a `target="_blank"` link on a page we serve (the shared layout's navigation is the usual one), an OAuth popup, a link out to a real site: each used to open an Electron window with no toolbar, no prototype and no patches, which for a page of ours looked like somebody else's site and for a live page was a window outside the model. All of them are **pages of the same window** now, and nothing opens a second window any more.
