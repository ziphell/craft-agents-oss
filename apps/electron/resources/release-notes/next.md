# Pending Release Notes

This file accumulates release notes for the next unreleased version. PRs that add user-visible behavior should append a bullet to the relevant section here. Versioned files (`X.Y.Z.md`) are owned by the release skill — never create them in feature commits.

## Features

- **The mock can remember: a flow, not just a response** — a fixture answers the same thing every time, which is enough for one screen and not enough for "add to cart, then the cart screen shows the item". A path item can now say which collection it is about (`x-mock-collection: cart.items`), the starting state lives in `services/{svc}/state.json`, and **what each method does follows from HTTP itself**: `GET` reads (the collection, or the element a trailing `{param}` picks by a field of that name), `POST` appends the request body, `PATCH` merges it, `PUT` replaces, `DELETE` removes the element. No transition language to learn: the contract stays ordinary OpenAPI. A read answers what the path addresses and a change answers the collection as it now stands — the screen that just added or removed something has to draw the list next — `x-mock.fixture` still decides the body when one is named, a missing element is a **404**, and an operation whose body contradicts the store answers **500 with a note** rather than looking like the app's own bug. An operation the vocabulary cannot express (`DELETE` on a collection, `POST` on one element, a `{param}` in the middle of a path) is refused when the contract is read instead of being mocked into something plausible. The store is held in memory and `state.json` is never written back, so **every apply starts the flow over** — which is also how a demo is reset. The delivered carriers ship the same state machine, so a `POST` that runs in the page changes what the next screen sees there too. Two edges changed while doing this: matching is now one rule for both the workbench and the page (a route matches the end of a pathname, so a `baseUrl` prefix still hits, and a four-segment route can no longer swallow a longer path), and `services/{svc}/state.json` belongs to the data writer alongside the fixtures. Good to know: the semantics exist twice — TypeScript for the workbench's network-level interception, generated javascript for the page — and one test table runs both to keep them from drifting.
- **A command can name a file instead of pasting its source** — `browser_tool` takes `--file <path>` on the two commands where a script otherwise had to be spelled out inside the call. `evaluate --file prototypes/cart/patches/ui-002-total.js` runs a local script in the page: the file is written once (with the Write tool, or it is the patch that already exists) and the same code never has to be produced a second time inside the command, nor re-escaped through the command string. A relative path counts from the workspace root, `~/…` is expanded, a BOM is dropped, and the answer says which file it ran and how many characters that was; over 256 KB is refused rather than shipped. It is a probe and says so — what it runs is not registered, so a reload drops it. `apply --file <path>` is the other half: it puts one patch on the page **and registers it**, leaving every other registration alone (a whole-set replay clears and re-adds them, which for a single file would un-apply the rest on the next load), and reports the `@target` matches for that file only. It names the file's own page when that differs from the page the command acted on, because a patch belonging elsewhere would otherwise read as a set of wrong selectors. A file that is not a patch of that prototype is refused **by name**: the injector ignores such files silently on a whole-set replay, and "named explicitly and quietly ignored" is the one outcome nobody can debug. Both flags exist for the same reason — an agent iterating on a patch was generating the same source twice per round and paying for it in context.

- **`reload` — the tab a conversation works from, reloaded** — the other half of the same loop, and of "that patch is already inlined here, reload to see the change": there was no command for the reload it kept asking for, so an agent could only `navigate` to the same address and hope. `reload` acts on the tab the command acts on (your tab, or the one `--tab` names), like the browser's own reload button — fire-and-forget, so it returns as soon as the reload is asked for rather than pretending the document is loaded: it says which URL it is reloading, tells you to `wait network-idle` (or wait on a selector) before reading the page, and that every `@eN` ref from before is stale. A batch stops at it for the same reason it stops at `navigate`. It is what makes a page of ours pick up an edit — the host renders it from disk, so a patch whose *contents* changed, which `apply` correctly reports as already inlined, becomes visible on the next render.

- **Element picker for browser_tool** — new `pick` command: the agent asks you to click an element on the page and gets back a stable selector (`data-testid` → `id` → `:nth-of-type` path) plus tag, text and viewport rect. Cancel with Escape or `--timeout <ms>`. Runs through the existing CDP session, so it needs no permission changes and stays sandboxed.
- **Argue with the work, and know what a round changed** — two new artifacts make a prototype's *disagreements* and its *acceptance history* readable instead of living in the conversation. `reviews/` holds one dispute per file (headed `# D-001 …`, then `about:` / `status:` / `claim:` / `evidence:`), where `about:` names a patch, a page, an endpoint or a requirement, and a patch dispute records the patch's fingerprint as `on:` so a later reader can tell an argument about the current file from one about a version that no longer exists — `status` reports such a dispute as **stale**, and reports `fixed` on a file that has not changed the same way, because a record that disagrees with the files is the thing worth surfacing. `verify` now records each run (`acceptance/state.json`, written by the tool alone) and `dist/acceptance.md` says which **round** it is and what *moved* since the round before — newly red, still red, fixed, no longer looked at, no longer declared — because a count cannot tell "this change broke it" from "it was already broken". `status` ends with what is still owed (a requirement nothing implements, a dispute nobody answered, a check that failed), `export` names the same list when it builds the package, and `export --strict` refuses to build at all while anything is — the mode for a run nobody is watching.
- **Prototype patches that survive a reload** — new `apply <slug>` / `clear <slug>` commands replay a prototype's patch files (`{workspace}/prototypes/{slug}/patches/{writer}-{nnn}-{name}.{css|js}`) into the browser. The patch index is recomputed from disk each time, so editing or deleting a patch file and re-running the command is enough. Patches are applied to the current page and registered for every future document, so a reload keeps them. Requires the patches directory to be writable in the current permission mode (`prototypesFolderPath` is now an Explore-mode write target).
- **Prototype export** — new `export <slug>` command builds the deliverable into `prototypes/{slug}/dist/extension/`: a loadable Chrome extension (load it unpacked from `chrome://extensions`; nothing is published to a store) that applies the patches to the live pages it covers and ships the prototype's own documents. The contract's `x-mock` responses travel with it, so a prototype built against the mock layer still works once handed over, and `README.md` says where it applies, which requests are faked and which build it is. `dist/dev-spec.md` still lists every patch in replay order, now grouped by page.
- **API contracts as a first-class deliverable** — new `contract-compose <slug>` / `contract-export <slug>` commands. Contract fragments under `prototypes/{slug}/services/{svc}/paths/*.yaml` are the source of truth (alongside `fixtures/*.json`); compose merges them into one `openapi.yaml` (reporting duplicate paths and `x-mock` fixtures that don't exist), and export writes the backend handoff into `dist/`: `openapi.yaml`, `contract.md` and `fixtures/`. `contract.md` lists endpoints and declared error responses, and explicitly flags what is *not* declared (no error responses, no `authType`, no pagination/idempotency/concurrency notes) so an incomplete handoff is visible instead of silent. No new dependencies.
- **Contract-driven network mocking** — new `mock-apply <slug>` / `mock-clear` commands serve the contract's `x-mock` responses through CDP `Fetch` interception, so the prototype runs before the backend exists. Interception happens in the browser's network layer: `fetch` and `XMLHttpRequest` (axios) are both covered, the app needs no mock-server URL, and fulfilled responses carry CORS headers. Endpoints without `x-mock` pass through; routes whose fixture file is missing are skipped and reported rather than served empty. No new dependencies.
- **Multi-page prototypes** — a flow is more than one screen. A prototype declares its other pages (`pages --add payment=https://app.example.com/pay` for one that belongs to a real site, `--rename`, `--remove`), and `export` scopes the delivered extension to **all** of them — one match pattern per live page, so a screen left out is an error rather than a page that quietly gets no patches. `status` lists the pages in flow order, `open --page <name>` opens one, and `snapshot` says which page a window is on. A page of ours is its own document (a top-level `.html` is a page), and every one of them ships in the extension under its own name — so the links an author wrote between pages keep working instead of 404ing in the package. (See "A prototype is a flow of pages" below: a page's kind replaced the prototype's.)
- **Prototype addresses are stable across restarts** — a prototype's page is served at `http://<slug>-<hash>.localhost/` (no port), answered by an `http` handler Electron registers on the browser session, instead of a loopback listener whose port changed on every launch. Anything that is not one of those hosts — real sites, local dev servers on `*.localhost`: everything — is passed straight through to Chromium's network stack unchanged. Because the origin no longer moves, a scratch prototype keeps its cookies and `localStorage` between runs.
- **`status <slug>` and artifact ownership checks** — a read-only report of a prototype: the pages it has and anything wrong with them, patches by writer (and how many are scoped to one page), per-service endpoint/mock/fragment/fixture counts, `dist/` contents, and ownership violations. Ownership makes parallel work safe by naming the paths where two writers could collide: a patch belongs to the writer named in its file name (`{writer}-{nnn}-…`), `services/*/paths/` and `services/*/fixtures/` belong to the writers their path rules declare, and `anchors/` and `acceptance/` are records only the tooling writes. Everything else in the folder belongs to the control plane (the agent) — a screenshot or a spreadsheet you keep beside `PRD.md` is material, not a breach. The check surfaces three things that were previously silent: a patch claiming the reserved consolidator prefix, misnamed patch files the replay scanner ignores, and stray files inside a service directory.
- **`open <slug>`** — opens a prototype in the browser: a live page goes to its own address with the patches replayed into it, and a page of ours goes to the prototype's own origin, rendered from that document with the patches it carries; with no entry page marked, it opens the page index. `--page <name>` opens a named page, and without it the open starts from the page the window is already on, then the entry page, then the index. Fails with the remedy named when there is nothing to open. Starting a prototype from nothing needs no special command — write `prototypes/{slug}/cart.html`, then open it.
- **A prototype is a flow of pages** — the `kind` moved from the prototype to the **page**, so a prototype is a table of pages and one flow can mix both: a page of ours (a document we own, `<name>.html` in the prototype) and a live page (someone else's address, patched in place). This replaces the per-prototype `kind` above. The sidebar lists a prototype's pages under it — click one to open it, mark one as the entry, rename or remove it — and the New Prototype dialog asks for a name only, with kind and address asked for when a page is added. `/` opens the **entry page** you marked, or a generated **page index** of every page when you have not marked one (with `/_index` always showing that index). Patches can be scoped to one page by directory (`patches/<page>/…`; `patches/*` still applies to every page), `apply` replays the patches of the page the window is on and says which page that was, and one export covers the whole flow: our pages ship under their own file names, each live page gets its own content script, the generated page index is the extension's options page, and the toolbar icon opens the entry page. Existing prototypes need no migration — old configs are read as a page table.

- **Requirements are read from `PRD.md`** — one requirement per entry, headed by a stable id (`## R-001 …`), and any patch header or page document declares what it serves with `@requirement R-001`. `PRD.md` is the **only** file read for requirements, and the name is exact — a lower-case `prd.md` is material, not a second brief. What sits beside it is yours: personas, the flow as it stands today, a glossary, a screenshot of the old screen — any format, any number of files, referenced from the entries. `status` turns the markers into the two answers nobody can get by reading files one at a time: a requirement nothing implements, and a marker naming an id `PRD.md` does not define. `dist/dev-spec.md` carries the same table to whoever receives the delivery, and names the changes that claim no requirement at all. The prototype page **renders `PRD.md` itself** rather than paraphrasing it — a PRD is prose written to be read, and a list of ids is not its argument — with one line per requirement saying what refers to it, and the rest of the folder listed underneath, one click from opening.
- **Research findings as files** — one finding per file under `prototypes/<slug>/research/` (`# F-001 …` plus `claim:`, `source:`, `captured:`, `evidence:`, `requirements:` lines). Evidence is checked against the disk, a finding with no `claim:` is reported, and neither findings nor frames are packaged: the reader receives the requirements, not the author's notes. A bound session's context now lists the requirements with what refers to each, and the findings recorded so far.

- **What a prototype keeps in view is a document you write, not a list the app keeps** — a prototype used to record what its work was built against as a maintained list of targets (`prototype-reference <target>`, with `list` printing `references:` / `referenced by:`, a References section on the page, and a block in every bound session's prompt). That tier is gone. It was a set of pointers **nothing pointed back at**: the only failure it could report was "this path is not on disk", which is a spell-check, and what it recorded — *this is what I studied* — the findings under `research/` already say, with the result attached; the one affordance it owned (click through to another prototype) is a click away in the sidebar anyway. What replaces it is the folder you already have: a file beside `PRD.md` — `references.md`, or whatever you call it — carrying a competitor's address, the path to a screenshot or a design file, or another prototype's slug, listed on the prototype page with its addresses and file paths clickable. The rule that mattered did not go with it, it just moved into the prompt and the guide: **another prototype's patch files are never copied into this prototype's `patches/`** — they were written against a different document, so their selectors would not match here, and every patch under `patches/` ships inside the deliverable.
- **Sample a recording into frames** — `sample-video <path>` reads a video you recorded elsewhere (a phone, Loom, QuickTime, a screen recording of a live session) and writes frames under `research/frames/<session>/`: numbered JPEGs, a `frames.json` index and an `index.md` table where each frame carries its position in the recording (`imported [0:12.4]`). `--every 2s` sets the interval, `--changes` keeps only the moments that moved, `--max 40` caps the frames and reports when it hit the ceiling. `--slug <slug>` aims it at a prototype other than the bound one. The recording is copied into `research/videos/` so the capture can be re-sampled later, and decoding is Chromium's — no ffmpeg — so a codec it cannot read (HEVC/H.265, ProRes, some `.mov`) fails with a message that says so. The frames come back **in the reply** as well as going to disk — a long sampling as a sample of it, first frame and last always in — because what reads a capture is a model, and a directory of files is something it never sees. The command is the only entry: sampling a recording is part of the same conversation as the finding that cites it.

- **Acceptance checks that run** — a requirement in `PRD.md` can carry `check:` lines (`check: selector [data-cart-total]`, `check: endpoint GET /api/cart`), and `verify` answers them: the selector against the page this session's window is on, the endpoint against the contract. With no page open the page checks report **skipped** rather than failed, and an unsupported kind is refused when the PRD is parsed instead of looking like a check that passed. The run writes `dist/acceptance.md` beside the change spec, and changes nothing else.
- **A project can note which prototypes its work touches — background, and the only project↔prototype relation there is** — the project detail page's **Prototypes** tab lists the workspace's prototypes, and any of them can be ticked as one this project works on (no agent command: it is the user's note). It is a **set**, not a choice of one: a project works on several prototypes at once, and nothing in the note says which is in front. That note is **background information, like a connected source**: the conversations in the project are told it (`<project_prototypes>`), and nothing else follows — no conversation is bound by it, no prototype context or guide is injected for one, and `prototype_tool` commands still take their slug from the page and the conversation's own binding. A prototype deleted behind the project's back drops out of the note instead of being mentioned with nobody able to open it. **A prototype belongs to no project**: the same prototype is routinely worked on from conversations of several projects, so the old "this prototype was made for project X" edge, the "which prototypes does this project have" list and the agent's `prototype-project` command are all gone — nothing on the prototype side records a project. A conversation that was already running when *its own* prototype changed still says so on its next message: the system prompt is pinned at the session's first turn (the SDK expects a session's prompt to stay put), so rather than let the agent keep working from a paragraph that describes the wrong prototype, it reports the change and points at a new session.

- **"Add to conversation" from the element picker** — the pick button turns selection **on and leaves it on**, and picking something is two steps. **Click an element and it is selected**: a solid box with its selector, staying where it is until you click another element, while the box that follows your cursor — dashed and lightly tinted — is only a preview of what a click would take. Both are drawn in your theme's accent colour, with the element's own name on a chip of it. Then the **"Add to conversation" button under the selection** puts that element in the composer as a **chip** — adding is only ever that button, so a stray click cannot send anything anywhere. Move to another tab of the window and keep picking: any page's elements can be selected, and each one carries the page it came from. It ends when you say so: Escape in the page, or the button again (the button shows the mode the window is actually in, so an Escape is reflected there too). Adding appends: a draft you were writing survives, and the chip shows what the element says, with its selector and its page on hover. When you send the message the chip is rewritten into a readable reference that says which page it was picked on, so what the model reads is a sentence rather than an internal marker — and a message with no text but a chip still sends. It needs no prototype and no bound conversation: the element goes to the conversation you are looking at, and if this workspace has none, one is opened for it. The prototype's own edit flow is unchanged apart from its prompt now going in above your draft instead of overwriting it.

- **A whole tab can be put in a conversation, not just an element of one** — the reference below, for a tab instead of a thing on it: "look at this page" is worth saying about a window somebody else may be driving, and a tab named as a chip needs no describing. Two ways in. In the top bar, **right-click a tab** in the window's tab list and choose **Add to conversation**. Or type `@` in the composer: the window's tabs are listed under **Tabs** — the title, with the prototype and page it belongs to (or its address) beside it, so two tabs with the same title are told apart — and picking one inserts the chip. It goes where a picked element goes, the conversation you are looking at, and the window is left exactly where it is. On send the chip is rewritten into a sentence naming the tab and its address, plus the prototype page it is when it is one's, so the model reads a reference rather than an internal marker.

- **A patch can now say what it is aimed at** — a patch header may carry `@target <css selector>` (alongside the existing `@requirement R-001`), and `apply` counts what each declared selector matched. It reports the two facts that used to be indistinguishable from "the change did nothing": a selector that **matched nothing and never has** (wrong selector, or the wrong page), and one that **matched before and does not now** — the page moved — with selectors that resolve to a single element on the page today, so a drifted patch is re-anchorable rather than only reportable. Each successful match is recorded under `prototypes/<slug>/anchors/`, which is what makes the second answer possible: the record keeps what the element looked like and when it last matched, so "it stopped matching" can be told from "it never did". The prototype page's page index shows each change's targets and flags a page whose selectors have drifted; `status` lists every patch with its page and targets and the state of each anchor record, and names patches with no `@target` as unchecked rather than reporting a clean run.

- **Edits show up in the open window without clicking apply** — saving a file under `patches/` or `assets/`, or changing a page document, replays that prototype into every window showing it: a page of ours reloads (the host re-renders from disk), someone else's live page is re-patched. Multi-file saves are coalesced into one replay, and the switch is in the prototype page's `…` menu — on by default, because "I saved the patch and nothing happened" is the failure this removes, and off when a window holds something you would lose (replaying a live page reloads it).

- **A copy can arrive with its change layer already folded into one** — a prototype's change layer is a patch per change, replayed forever; collapsing it into what owns it is the inverse of appending yet another patch. The place it happens is **copying**: a prototype's row menu offers *Duplicate* and *Duplicate with the changes folded in*, and only the copy is ever folded — the prototype it came from is left exactly as it was. On a copy's page of ours the CSS is folded into `assets/<page>/committed.css` and the scripts are promoted into `assets/<page>/committed.js`, both referenced from the document; on a live page (whose address we can never rewrite) everything is folded into `patches/<page>/Z-001-upper.css` / `Z-002-upper.js`, which replay after every other patch by rule. Each folded change leaves a provenance header naming where it came from and carrying its `@target`/`@requirement` markers, so the anchors and the requirement thread survive the fold; the patch files that were folded are then deleted. The whole prototype is folded in one go, and a copy with nothing left to fold says so rather than writing an empty file. There is **no command** for this and exporting never folds: the package carries the change layer as you left it.

- **A window holds more than one tab** — opening a prototype no longer replaces what the window was showing: `open`, the prototype page's Open button and a prototype address typed into the address bar each open a **tab of their own**, so two prototypes can be worked on side by side instead of one at a time. Every window has a **tab rail down its left edge**, running the full height of the window with the address bar to its right — the back button and the address start where the tabs end. It holds one row per tab with its title, the tab on screen raised, a close button on each, and a `+` for a new one — always, including with a single tab, because that `+` is how you open something yourself; the tabs are the topmost thing in the window, so nothing covers them. It is a column and not a row across the top on purpose: tabs are a list that grows with use, and a row has to share its width with the address bar — a second tab scrolled the bar aside and pushed the tabs after it out of sight. The chrome's colours are the app's throughout: a tab that paints itself dark no longer repaints the address bar and the rail beside it (the window's own chip in the top bar still takes the tab's colour, which is about *which* window it is). The window's badge in the top bar lists the same tabs under it (marked with a count), so a window that is not in front can still be switched tab by tab. `tabs` lists them for the agent, `tab-new [url]` adds one, `tab-close <id>` closes one (closing the last closes the window), and any command can name the tab it acts on with `--tab <id>`. Naming a tab is a **target, not a request to move you**: the command acts on that tab wherever the window happens to be showing, and `tab-show <id>` is the command that brings one up for you to look at. A window that has just been created is opened *into* rather than beside: its own blank tab is what a window is made of, so a freshly opened prototype is one tab, not two.
- **The browser is one window per workspace** — every conversation in a workspace, and you, now share a single browser window, with each one a **tab** instead of a window of its own. Ask two conversations to look at two different prototypes and they end up side by side in the same window rather than in two windows; open a tab by hand and it lands in that same window. It is not a prototype thing: the same window is where a general task's browsing happens. `browserPane` resolves the workspace's window for everyone, so "which window is mine" stopped being a question — a window now carries only *who is driving it at the moment* (a lease, renewed by every command and released when a turn ends). Two things follow: who is driving a window is a **lease** (`driven by`, per tab in `tabs`) rather than a lock — the window is shared, so there is nothing to lock — and `close` on that window means "close the tabs you opened" rather than closing it, which is what "don't close the user's things" means once the window is everyone's. Workspaces stay apart: each has its own window. The agent's `windows` command is gone with it: there is one window per workspace, so there is nothing to list (`tabs` answers the tab-level question, and the app's own window list is in the top bar).
- **Opening a browser opens a tab** — the top bar's "New Browser Window" is now "New tab", since there is only one window to put it in. A tab the agent opened in this window is marked with a small icon in the tab rail.
- **Which prototype a tab is for now comes from the tab** — with a window holding several prototypes' tabs at once, `snapshot` names the prototype of the tab **it is about** (recorded when it was opened, which is the only fact that survives an overlay loading a third-party site) instead of the conversation's binding, which is now only the fallback for a tab that belongs to none. `prototype_tool` commands with no slug mean "the prototype of the tab you work from", so one conversation can drive several prototypes without declaring any of them: `--tab <id>` picks the tab, the tab says whose it is. Existing behaviour is unchanged for a single-prototype conversation.
- **Each tab says what it is, who asked for it and who is driving it** — `tabs` prints, per tab, what the tab itself reports (its real address, its title, whether it is loading, which prototype it is for and which page of that prototype it is on) and, separately, what is stated about it: `opened by: agent (session-…)` or `opened by: a person`, and `driven by: <session>` or `nobody right now`. The three are kept apart on purpose — one is measured, one is intent, one is a lease (who is working on this tab at the moment, released when their turn ends) — and the first two are what let a conversation tell its own tabs from everybody else's. Tabs the agent opened are marked with a small icon in the window's tab rail, and a tab some conversation is working on right now gets a dot.
- **A conversation can only work on — and close — what is its own** — the tab-level half of "don't touch other people's things". A tab is yours to work on when it belongs to no prototype (an ordinary tab: anybody's, which is what "you open it, the agent takes over" means for a tab that has nothing to do with prototypes), when it is for the prototype this conversation works on, or when this conversation opened it. Another conversation's prototype is refused, and the refusal names it and says how to bind it. Closing is narrower still: only tabs **this conversation opened** — the user's tabs and another conversation's are not yours to close however convenient it would be. `close` on the shared window therefore stopped being a flat refusal: it closes the tabs you opened (leaving a fresh tab if they were all of them) and says so, while the window itself stays — it belongs to the workspace.
- **A link that wants its own window opens a tab beside the one that asked** — `target="_blank"`, `window.open`, popups and a prototype's own links all become **tabs of the same window**, inserted right after the tab they came from, instead of bare Electron windows with no toolbar, no prototype and no patches. Which kind it was is recorded per tab (`opened as: a popup (no window.opener here)` / `a link that wanted its own window` in `tabs`), because there is one cost worth being able to name: a tab opened this way has no `window.opener`, so a popup waiting for a `postMessage` from the tab that opened it — Google's sign-in is the usual example — will wait forever. Such a tab also cannot close itself (Chromium only lets scripts close windows that scripts opened), so it stays in the tab rail until you or the agent closes it. A `background-tab` request is added without coming to the front.

- **A shared window shows whose tabs are whose** — the tab rail sections its tabs by who opened them: your own under *You*, and one section per conversation (named by that conversation's title) for the tabs an agent opened. The same sections appear in a window's tab list under its badge in the top bar, because both draw the same rule. Headers appear only when there is more than one group — with everything yours there is nothing to tell apart — and tabs keep their order, so the sections read in the order the tabs were opened. It is a view and nothing more: whose tab it is remains the tab's own record, and no rule about what you or an agent may touch changed.

- **The tab being worked on is locked — the window is not** — while an agent works on a tab, that tab takes no clicks or keystrokes, and another conversation's command that names it is refused until the turn ends. Everything else stays yours: the tab rail, the address bar, the window's size, and every other tab. It is the same lock this used to put on the whole window, one level down — a window is shared by the whole workspace, so holding the window held your own browsing and everybody else's tabs with it. The locked tab is marked in the rail and named in `tabs` (`locked: <session> is working on it`), and you are never stuck behind it: that mark in the rail is a **button**, and clicking it lets go (the agent keeps its turn and may take the tab again on its next action). The lock is dropped automatically the moment the tab it holds goes away, so it can never point at something that no longer exists.
- **A conversation works from its own tab, not from whatever you are looking at** — a command that names no tab now lands on the tab that conversation has been working from (`tabs` marks it `your tab`), and only on the tab on screen when it has none yet — which is the takeover case, and from then on that becomes its tab. Switching tabs in the window is therefore safe: what you look at is yours to move, and it no longer pulls somebody else's work somewhere else. Naming a tab with `--tab <id>` is how a conversation moves its own.

- **A tab's task is inherited** — a tab a link or popup opens belongs to whatever the tab it came from belongs to, so a conversation's tabs are a **task group** rather than a list it happened to open: a link it could not follow itself still lands in its group. Who clicked is not asked — an agent's click and a person's look the same from here — because the tab it came from answers it. A tab opened from a tab nobody owns stays nobody's. Two consequences worth knowing: those tabs are listed under that conversation in the tab rail, and closing that conversation's tabs closes them too. `tabs` says `belongs to: …` for the same reason it no longer says "opened by": after inheritance, who *opened* it is not what the line means.

- **A tab in the background is a real tab — and only the one being worked on pretends to be in front** — a tab that was not on screen used to be parked at zero size: no viewport (coordinates in it meant nothing) and nothing painted (a screenshot of it came out empty). Tabs now keep the content area and are stacked under the one on screen, and the tab a conversation is working from is told it is in front, so a site cannot behave differently just because you switched tabs (measured: `hidden` and 2 frames in 2.5s before, `visible` at full frame rate after). Memory is the same either way — 613MB parked against 614MB for four tabs — so what this saves is CPU: the tabs nobody is working on stay throttled.

- **The agent works in its own tab, and your tab stays yours** — a command no longer comes to the front of the window to run: it acts on the tab that conversation works from, wherever that tab sits, and only `tab-show <id>` moves what you see (which is what it says). Opening a tab with `tab-new` or `open` opens it **behind** the one you are reading, so the window you are using is not taken away while a conversation works somewhere else in it — the tab is listed in the rail either way, and the agent's summary says which one it opened. It is the same rule at every level: a click, a screenshot, a console read and a patch replay all land on the conversation's tab, and the automatic replay after a file change reaches every tab showing that prototype rather than whichever one happens to be in front. `tabs` still says which tab is yours (`your tab: …`), and `--tab <id>` names one for a single command without moving anything.

- **A prototype's delivery now includes a static file, not only an extension** — `export` also writes `dist/static/`: every page of ours as one self-contained HTML file, with its patches, the mock layer, and every reference it makes to a file of the prototype (a stylesheet, a script, an image, a font) inlined into it. It is built with the preview's own transform, so it is the page the author saw, and it asks nothing of the reader: no host, no extension, nothing to load — double-click it, or send the file on. Page file names are kept and a link to another page stays a link, so a flow of ours still walks from one file to the next. A reference that names no file of the prototype is reported under its own heading, rather than left as a link that breaks the moment the file is opened on its own. A prototype made only of live pages has no `static/` folder: a live page runs its own code and carries its own session, so a copy of it would only look like the page — that half stays the extension's job.

- **Images, fonts and video now reach the extension too** — a prototype's own static files under `assets/` used to travel only if they were text: the package was a table of strings written as utf-8, so a png was dropped with a warning and a page of ours lost its images the moment it was loaded as an extension. The package now carries the whole of `assets/` copied **verbatim**, bytes and all, under the same paths the pages address them by — so `/assets/logo.png` simply resolves. Nothing is filtered by extension any more, because whether an asset is used cannot be told from the markup: a script builds the URL, a stylesheet pulls in a font.

- **The live pages can also be handed over as bookmarks** — `export` writes `dist/bookmarklet.html` for a prototype with live pages, for the browser where an unpacked extension cannot be loaded at all (a managed one, someone else's laptop, one look). It holds one draggable link **per live page** — each carrying the same bundle the extension ships and the same mock layer, so the two carriers cannot diverge — plus that code printed underneath for the console, because those are the two ways a bookmark fails: a page sending `script-src 'self'` refuses an inline bookmark outright, and the console snippet is the way round it. One link per page rather than one for the flow, since a bookmark is not scoped to an address the way a content script is; the page says which address each link is for, and states what this carrier gives up (a click per page, per reload). A prototype whose live pages have nothing to apply gets no file: a bookmark that does nothing looks like it worked.

- **The prototype commands are their own tool (`prototype_tool`)** — they used to be `prototype-*` subcommands of `browser_tool`, which made one tool cover two subjects: driving the window's pages, and working on a prototype's own files (a third of those commands never touched the browser at all). They are now `prototype_tool`, and `browser_tool` keeps the window's own surface — refs, snapshots, input, console, network, tabs. Nothing about the machinery changed: both go through one runtime and one window, `open` still adds a tab to the window you are already using, and `--tab` still names which one a command acts on. What changed is the name on the door, and with it that each door carries its own description, its own `--help`, and its own guide — so a session is told how a prototype's files and its window work before it runs one — and that a command one door does not handle is answered by name with the tool that does take it. The commands lost their prefix with the move (`prototype-apply` → `apply`): both tools take bare command names, so `browser_tool open` and `prototype_tool open` are told apart by which tool you call, not by the word. One command per call: the prototype tool does not batch.

- **Prototypes have their own guide, alongside the browser's** — the prototype workflow no longer has to be pieced together from the browser guide and the tool description. A new bundled doc (`~/.craft-agent/docs/prototypes.md`, synced on launch like every other doc) covers it end to end: what a prototype is (a flow of pages, each `scratch` or `overlay`), the directory layout, who owns which artifact, `PRD.md` and the documents beside it / `research/` / `reviews/`, the patch naming rule, folding the change layer (an option of copying, never a command), verification, contracts and mocks, the deliverables, and the full command reference. A conversation that is bound to a prototype gets **the whole guide injected** — it is the case the guide is written for, so the rules are in front of the agent instead of being a step it may skip — while every other session gets the general model and the pointer, so one that starts a prototype is not starting from nothing. The browser guide keeps a pointer to it, and the system prompt names it next to the browser guide with the workflow's first steps.

## Improvements

- **The prototype page index looks like a product, not a debug listing** — the list `/` falls back to (and the extension's options page, which is the same document) now shows each page as a row: its place in the flow, its name, `scratch` or `overlay`, which one is the entry, and the file or address it opens — a row you can open is a card you can click, and a page whose document is gone keeps its place and is visibly not openable. It follows the system theme, so it reads the same in light and dark.

- **`status` lists what each patch is aimed at**, and reports anchor records that outlived the patch that declared them — a record nothing refers to any more is named rather than left looking checked.

- **A prototype page says what is still owed, not only the agent** — the same verdict the agent gets is now on the screen that hands the work over: the header carries a **Delivery** button, and what it opens is the outstanding list (a requirement nothing implements, an objection nobody answered, a check the last round failed, checks that have never been run at all, or a service whose contract declares a mocked response the prototype does not ship — that route is skipped, so the request reaches a backend the recipient may not have), each line saying where to go to settle it — jump to the section, or hand it to the conversation — followed by one line per service and the `dist/` contents the next export will write. The prototype list's status dot counts the same thing, so a row no longer looks finished while something in it is still owed, and `Export` now names what the package could not carry instead of succeeding with those warnings dropped on the floor.

- **The delivered package now includes its own index — `dist/handoff.md`** — `export` writes it last, so it lists what that run actually produced: a table of artifact → who it is for → what to do with it (`dev-spec.md` first, then the extension or `static/`, the bookmarklet, `acceptance.md`, the backend's `contract.md` / `openapi.yaml` / `fixtures/`), which page the flow starts at, and a closing section restating **what the delivery does not settle** — the same list `export --strict` refuses on, on the package's first page rather than at the end of a spec nobody read that far into. It is the file a recipient should open first, and the command's output names it.

- **`dev-spec.md` reports what each `@target` matched** — every change in the spec now carries its selector's health, read from the anchor record rather than guessed at: how many elements it matched and when, that it was recorded and matches nothing now — the page moved, together with the fingerprint's candidate selectors for where that element went — or that nothing has ever seen it match. A change with no `@target` says so. This is the fact the recipient cannot get anywhere else, and the one that decides whether a change can be translated into source as written.

- **A service that keeps state says so where its contract is read** — `status` prints `N keep state` for a service whose contract declares collections. A service of fixed answers and one whose screens depend on each other are different things to build against, and until now the two read identically.

- **A generated plan no longer puts two nodes on one page** — the task generator now knows the range of a node's `writes:` identity: it guards the files a writer owns (their patches, their service fragments, fixtures and state), while the shared control-plane files — page documents, `config.json`, `PRD.md`, `dist/` — are writable by whoever is writing, by design. So it keeps those to a single node, or gives each node its own page, instead of emitting a race that nothing guards. Two writers on one prototype is the case this makes safe: their patches cannot collide (a duplicate identity is refused when the task is validated, and a name claiming someone else's prefix is refused before the write).

## Bug Fixes

- **The acceptance report no longer goes quiet when a PRD drops its last check** — the report ended with "No checks yet" whenever a run answered no checks at all, which is right on a first run and wrong in the case that matters: a requirement whose `check:` line was deleted. That is a criterion nobody is verifying any more, and it now says so — "No longer declared" with the check named — instead of reading like a prototype with nothing to check. The two empty runs are kept apart, because "never had one" and "had one and it is gone" are different facts.

- **A link that opened a bare window now opens a tab** — a `target="_blank"` link on a page we serve (the shared layout's navigation is the usual one), an OAuth popup, a link out to a real site: each used to open an Electron window with no toolbar, no prototype and no patches, which for a page of ours looked like somebody else's site and for a live page was a window outside the model. All of them are **tabs of the same window** now, and nothing opens a second window any more.

- **"New tab" adds a tab, and the window comes up on it** — a window that is already open now gets a real new tab, brought to the front, where before a window holding one untouched blank tab read as "not opened yet": the request was answered by that tab, which had nothing to load, so the click did nothing at all. A window that is not up yet still opens into its own blank tab, so a fresh window never comes up with two of them. The window's tab list under its badge in the top bar now lists whatever the window holds, **including a single tab** — it used to keep quiet about a one-tab window, which is exactly when you want to know what is open — and "New tab" sits with the window's other actions rather than inside the list, so it is there either way. An entry in that list shows its tab and brings the window up with it, so a window that is behind something else is reached from the top bar.

- **A new tab no longer shows the tab that was there before** — a tab that is made and left with nothing in it draws no pixels of its own, and the window's tabs all sit in the same place, so switching to it showed whatever was underneath: a tab opened from the top bar, and a `tab-new` from a conversation, both left you looking at the tab you were already on. Every tab is now given the "New Tab" page the moment it is made, whichever way it was opened. A tab that is closed now leaves the window as well: its view used to stay behind — still drawing at the content area, and still costing a renderer for a tab nobody could name.
