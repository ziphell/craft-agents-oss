# 产品经理需求生产工作台 — 实施方案

> 状态：**定位已收敛**（2026-09-25 重写）。本文件只写"这是什么、边界在哪、为什么这样"。
> 实现细节、踩坑、以及已经删掉的机制见 [开发文档](prototype-workbench-dev.md) §4 墓园。
> 本文件是重写的：旧版（补丁 / 页 / 宿主 / mock / 契约 / 交付物那一整套）已整份删除，它的思路留在 git 历史里。

---

## 1. 定位

**一句话**：把**需求**和**实现它的文件**绑在同一个文件夹里的规格工作台——人写规格，agent 在同一处实现，工具只回答两句话：**哪个需求没人实现**、**哪个引用指向不存在的需求**。

三条具体含义：

- **人写规格**：markdown 里逐条编号的需求（`## R-001 <标题>`）——一个文件或几个，写在文件夹里任何 `.md`（子目录也算），`PRD.md` 只是惯例的起步文件；旁边放材料——截图、表格、竞品地址、词汇表、旧版流程，任何格式，没有规则。
- **agent 用普通文件工具在同一文件夹里实现**：没有专属运行时，没有"应用 / 执行 / 部署"这个动作，没有需要先跑起来的容器。它写的就是文件。
- **交付物就是这份规格本身**：一个文件夹，人、agent、后端都能直接打开读。

**与 Pencil 的关系**：不是"替代画布"，而是另一种活。Pencil 在空白画布上无中生有，产出设计或代码；这里不生成任何可运行物，它让**需求和它的实现长在同一处**，并且随时能问出"还差什么"。核心差异仍是载体——但现在的载体不是浏览器引擎，是**文件夹**。

**与"原型"这个词的关系（命名张力，明说）**：以前"原型"意味着会跑的页面、注入的覆盖层、契约、mock、可交付的扩展包；那些都删掉了，剩下的东西其实是一份**规格**。名字暂时不动（改动面太大：目录名、工具名、界面文案、locale），但本文与代码里的"原型"一律指 `prototypes/<slug>/` 这个文件夹，**不要按旧含义读**。

## 2. 一个原型是什么（唯一的数据模型）

一个文件夹，四类内容，没有第五类：

| 内容 | 形状 | 谁写 |
|---|---|---|
| 规格 | 一节一条需求：`## R-001 <标题>` + 正文（正文随便写）；写在文件夹里**任何 markdown 文件**（一个或几个，子目录也算） | 人（也可以让 agent 起草） |
| 旁边的材料 | 任何格式，任何数量，没有命名规则 | 人 |
| `research/` | findings：一条一个文件，`# F-001 <一句话结论>` + `claim:` / `source:` / `captured:` / `evidence:` / `requirements:` | agent |
| `reviews/` | disputes：`status:` + `about: requirement R-001` + `on:`（需求指纹） | agent（人改 `status:` 裁决） |

**没有别的目录**：没有配置文件、没有索引文件、没有状态文件、没有 `services/`、没有 `dist/`、没有 `patches/`、没有页表。

**唯一机制**是 `@requirement R-00x`：写在文件夹里**任何文件**里（注释、字段、文档），就算"这个文件服务于那条需求"。需求 ↔ 实现的连接**不存第二份**——没有登记表，没有清单，读的时候现算。这是这份规格能被 agent 和人**同时**读的原因：两边看的是同一批文件。

两条由此而来的规矩：

- **需求来自任何 markdown 文件的 `## R-00x` 标题，不是某个文件名**：文件名不决定是不是规格（`PRD.md` 只是 `create` 的起步名），子目录里的 md 也算；写进非 markdown 文件的不算需求。定义需求的文件不算实现它——否则规格会把自己写下的需求标成"已实现"。
- **需求编号是唯一的锚**：某个文档里定义了才有意义；指向没定义的 id 会被点名，同一个 id 被两个文档定义也会被点名。

**文档之间可以互指**：用**普通 markdown 链接**——`[结算流程](docs/checkout.md)`，从本文档所在目录再原型根（`../PRD.md` 也可）——这就是"入口文档索引几份文档"的做法，而且这一行在别的读者（同事的编辑器、GitHub）里同样是链接。链接只负责**导航**：它不改变"哪条需求实现了"（仍只看 `@requirement`），链不到会被点名，反链在详情页可见。

## 3. 命令面：3 个

| 命令 | 做什么 | 落盘 |
|---|---|---|
| `list` | 列出这个工作区里的原型（各自的文件/需求计数），以及本会话绑定的是哪个 | — |
| `create <name> [--no-bind]` | 建文件夹 + 一份起步 `PRD.md`；默认顺手绑定本会话 | `prototypes/<slug>/PRD.md` |
| `status [slug]` | 报告：需求 × 依据、findings、disputes、还欠什么（见 §4） | — |

三个命令**都是文件活**：没有一个需要浏览器、窗口或任何运行中的东西。实现、findings、disputes 全部由 agent 用 Write/Edit 写；`create` 只建文件夹与起步 PRD。

界面那一侧另有一组 RPC（`prototypes:list / create / duplicate / delete / watch / unwatch / changed`）：**`duplicate` 与 `delete` 只有界面用**，没有对应的 agent 命令——复制一份原型、删掉一个是人的动作。

## 4. 报告：`status` 说什么

一段一段，都是现读现算：

- `dir:` / `spec:` 目录的绝对路径、定义需求的文件（一个或几个；还没有就明说"还没写"）。
- `requirements:` 每条需求一行——**谁引用了它**（文件、findings）、`disputed by`、以及 `on: <指纹>`。
- `files:` 文件夹里的文件（不含 `research/`、`reviews/`）。
- `findings:` 有几条、分别在哪。
- `issues:` 读不干净的地方——指向不存在的需求 id、finding 的 `evidence:` 不在盘上、评审文件缺字段。
- `reviews:` 总共几条、几条还立着（每条写明它异议的是什么、为什么 stale）。
- `unresolved:` **还欠什么**，最后一段，因为它是行动项。

**门禁只数事实，不数主张**（`whyPrototypeIsNotSettled`）：有需求没有任何文件引用它、有链接指向不存在的文件。两条都没有时，**页面与列表什么都不显示**——"可交付"不是要声明的事，一个还没有需求的原型同样满足这两条，所以过去那句"可以交出去"其实是在替一件还不存在的工作打包票（用户指出的）。只有还差着什么才值得显示。

**异议不进这个门禁。** 使用人是驱动 agent 的产品经理，写规格的和提异议的是**同一个 instrument**；而"这条异议成不成立"工具判断不了（它不猜、不评分）。把异议算成欠款有两个后果：agent 写一个文件就能把自己的交付堵住；人只能用改一个 `status:` 字段来放行——那不是决定，是静音。所以异议**报但不判**：它按需求挂在详情页、在 `status` 的 `reviews:` 段落里点名（`unresolved:` 不含它），随交付物一起走到下一个读者手里。

`on:` 那个指纹是需求的**内容指纹**：它写进 dispute 的 `on:` 行，需求被改写后指纹就变，于是"这条争议是针对现在这版需求的，还是针对已经被改掉的旧措辞"能分得开。

**它不做什么**（都是有意的，不是没做完）：不写文件、不产出交付物、不执行任何检查、不记历史——**跑一次看一次**，没有"上一轮"可以对比。

## 5. 人 / agent 的分工

- **文件夹里的内容由 agent 用普通文件工具（Write/Edit）写**；人当然也能直接改——拿编辑器改，或者让 agent 改。应用里**没有**内置编辑器（那是刻意删掉的）。
- **人**：写需求、放材料、看 `status` 与详情页、裁决争议（改 `status:`）、绑定对话。
- **绑定**：一个对话绑到一个原型后，系统提示里带一份 `<prototype_context>`（需求 + 谁引用了它们 + findings），所以 `prototype_tool` 的命令不用背 slug；没绑定就点名。
- **项目只记"这个项目碰过哪些原型"**：背景信息，不绑定、不继承、不注入上下文（`project-link.ts`）。原型不属于任何项目——同一个原型常被多个项目的对话使用。

---

## 6. 明确不做的（非目标）

- **不生成任何可运行物**：不导出扩展包、不自包含 HTML、不做书签、不打包。
- **不做 mock / 服务契约**：没有 `services/`，没有 openapi，没有 fixtures。
- **不执行验收**：没有 `check:` 机制、没有 `verify`、没有验收报告（`check:` 现在只是正文，解析器不认识它）。
- **不碰浏览器**：页面、补丁、注入、宿主机、地址，全是 `browser_tool` 的事；本工具一次窗口都不需要。**目前唯一一处例外**是 drawio 的 viewer/editor——app 自带的一份 webapp 在自有 origin 上被服务，工作台里放一张 frame 接它（代价与依据见[开发文档](prototype-workbench-dev.md) §7.3）。
- **不记历史**：没有轮次、没有 diff、没有状态文件。
- **不做写归属 / 写守卫**：原型就是一个文件夹，谁都写。
- **不做**画布 / 拖拽设计器 / 云端 / 协作 / 权限 / 账号。
- **不引入 git**：产物就是本地文件，版本由人自己的工具管。

## 7. 为什么是现在这个形状（决策回顾）

每一条都是"曾经有、现在没有"，一句话说为什么；展开见开发文档 §4 墓园。

- **一切皆文件 ⇒ 平面分离没有对象了**。曾经四个平面（数据 / 控制 / 业务逻辑 / 渲染）是为了让多 agent 并线成立；现在渲染面与业务面根本不在这个工具里，数据面就是文件夹，控制面就是 agent 自己。
- **并线的瓶颈原本是写冲突，而冲突源被删光了**。契约片段、状态文件、补丁索引、页表——当初需要"写身份 / 路径归属"是因为这些东西会被两个写者撞上。它们都不在了，剩下的冲突只是"两个对话改同一个文件"，那是文件系统的问题，不需要这个工具发明机制。
- **验收 / 契约 / 交付物是给机器和后端的**，而这份规格的读者是人 + agent。所以 `check:`、`verify`、`acceptance.md`、openapi、contract.md 一并删掉：它们回答的是"后端怎么实现"和"检查有没有跑过"，不是"这条需求做完了没有"。
- **补丁与页是"在看真实产品时改它"的产物**，那条能力整体属于浏览器工具（`browser_tool`），不该长在规格的文件夹里。
- **抽帧是"让 agent 看一眼录像"**，与原型无关，已提为顶级工具 `video_tool`。
- **不记历史是刻意的**：判据是"现在这份规格还欠什么"，而一份记不住上一次的运行报告只会让人误以为它记得。

## 8. 相邻子系统：这一轮一起动了什么

这一轮收敛的同时，两个**相邻子系统**也被改动。写在这里不是因为它们属于本工作台，而是因为**边界变了**：原本长在原型上的能力搬去了浏览器，网站拿到了自己的数据通道。

### 8.1 浏览器（`browser_tool`）

- **原来长在原型上的东西整份搬走 / 删掉**：原型宿主（`http://<slug>-<hash>.localhost/`）、页与页表、补丁与注入、**标签页上"它属于哪个原型 / 哪一页"的归属字段**，以及**网络层那套拦截**（CDP `Fetch` 域的 mock）——全部从代码里消失（墓园见开发文档 §4）。浏览器现在只做一件事：驱动一个窗口——页面、refs、输入、截图、console、network、tabs；一个标签页只带自己的地址、标题、console 与主题色。
- **它的文档不再提"原型"**：`apps/electron/resources/docs/browser-tools.md` 里整节原型删掉，连带删掉几句**在描述已不存在机制**的话（"标签页带着它所属的原型"、按标签页推断"这条命令说的是哪个原型"、`none of the prototype's pages` 那个报错）。`browser_tool` / `video_tool` 的"未知命令"提示也不再点别的工具的名字——几扇门靠**被调用的是哪个**区分，不靠消息做路由。
- **录制只有人工入口**：窗口工具栏的录制按钮是唯一入口（文件落在下载目录，mp4 优先）。曾经有一个 agent 侧的 `record` 命令，已删——录制存在的理由是"**now 是 agent 从被录的东西内部唯一供不出的**"，那是按钮的活，不是命令的活。
- **`video_tool` 提为顶级工具**（从 `prototype_tool sample-video` 长出来的）：`sample <path> [--out <dir>] [--every <ms>] [--changes] [--max <n>]`——Chromium 解码（不用装 ffmpeg），帧作为图片回到回复里，**不传 `--out` 就不写文件**。

### 8.2 网站（Websites）

这一项**与本工作台无关**，是同一轮里修的一个独立缺陷；记在这里，因为它占了"网站 / 浏览器改动"的另一半。

- **网站在浏览器窗口里打开，不再嵌在应用里**：它以前是应用内容区里的一个 `<iframe>`，配一套 `kind`（`static`/`interactive`/`live`）的 sandbox 分级和一条 `craft-websites/v1` 的 postMessage 桥。这三样都删了——点开一个网站 = 在浏览器窗口里开一个**真实标签页**（人的标签页；窗口没开就开一个并带到前台），因为一个真实标签页才既能跑站点自己的脚本、又能用上工具栏与调试。详情页保留头部与动作（重命名、数据新鲜度、导出副本、刷新预览、删除、绑定项目、打开文件夹、交给对话），只是不再有画面。
- **站点自己的脚本能读到自己的数据**：`fetch('/data/snapshot.json')`（在站点自己的地址上）返回已发布的数据快照 `{ version, generatedAt, kv, series }`。这是 `data/` 下**唯一**对外服务的文件（`store.sqlite` 等仍不服务）；**还没写过数据时是 404**——"还没有数据"，不是空数据集。没有推送方，所以站点要靠重取或重载来发现新数据。
- **导出副本带上这份快照**（导出那一刻的数据），因为站点的脚本会去 fetch 它；`website.json`、封面图、`store.sqlite` 仍不带走。
- **一条规则管两处**：`isWebsiteHostOwned()` 同时被"服务哪些文件"与"导出哪些文件"读。两处各写一遍就会漂——这正是当初站点拿不到自己数据的原因。

## 9. 验收：怎么知道它 work

端到端就一条闭环（跑一遍就够）：

1. `create` 建一个原型 → 2. 写两条需求进 markdown（一个文件或几个）→ 3. 让 agent 在文件夹里实现（文件里写 `@requirement R-001`）→ 4. `status` 应显示一条已实现、一条"nothing refers to it yet" → 5. 写一条 finding 并用 `requirements:` 引用那条需求 → 6. 写一条 dispute（`status: open` + `about: requirement R-002`）→ 7. `status` 的 `unresolved:` 里出现它、详情页徽章不再是"可交付" → 8. 把 dispute 的 `status:` 改成已答复 → 它消失 → 9. 删掉那个实现文件 → 需求又回到未实现。

边界也要对：

- 需求来自任何 markdown 文件的 `## R-00x` 标题（一个 md 或几个、含子目录）；写进非 markdown 文件的不算需求。
- 文件里写 `@requirement R-099`（没有文档定义它）→ `issues:` 点名。
- finding 的 `evidence:` 指向不在盘上的路径 → `issues:` 点名。
- 需求被改写 → 旧 dispute 的 `on:` 对不上 → 报告里说得清"它针对的是被改掉的措辞"。

## 10. 风险与仍开放的问题

- **命名**：现在是"规格"，名字还叫"原型"（§1）。要不要把目录名/工具名一起改，是一个独立决定，改动面覆盖界面与 locale。
- **"实现"的判据是约定，不是校验**：文件里写了 `@requirement R-00x` 就算实现。一个空文件也能让需求算"已实现"——这是有意的（工具不猜、不评分），代价是它只能回答"有没有人认领"，不能回答"做得对不对"。所以它必须和 reviews 一起用。
- **门禁只数事实**（§4）：需求没人实现、链接指向不存在的文件。没有"检查失败"这一档，因为没有任何东西在跑检查；也没有"异议还没答复"这一档，因为那不是事实。
- **能在真机上验的只剩界面**：详情页、列表、创建/复制/删除对话框、绑定选择器。所有命令都是文件读写，测试里覆盖得到。
