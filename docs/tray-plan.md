# 托盘（Tray）— 开发文档

> **定位**：本文写「为什么需要托盘」「它是什么、不是什么」「生命周期怎么变」「代码放哪」。它是**主进程的一块呈现面**，不重复 [设计方案](design-plan.md)（§2.7 独立窗口）或 [项目分层](project-layers.md) 已经定下的东西。
>
> **一句话**：关掉所有窗口后 app **仍然活着**，托盘就是它活着时的样子。先做**常驻的壳**（唤起 + 状态），design 停靠点与后台任务面按需长。
>
> **状态**：第一版已实现——关闭 = 隐藏（§3.1）、托盘壳 + 菜单（§4 / §5）、单实例守卫（§3.6）、**拉起最近窗口**（§3.2）、**启动一律显示**（§3.4）、**一个工作区一个窗口的上界**（§3.7）、有托盘才常驻的兜底。**未做**：未读徽标（§4，需要一个逐语言的新文案键）、② design 停靠点、③ 后台任务面。
>
> **读法**：§1 是判断（为什么是现在、为什么非做不可）；§2 是它是什么；§3 是生命周期；§4 / §5 是第一版的菜单与代码位置；§7 是还没定的。

---

## 1. 判断：为什么是现在

### 1.1 现状的矛盾

app 现在是**纯窗口制**：非 mac 平台上，最后一个窗口关掉就 `app.quit()`（`apps/electron/src/main/index.ts` 的 `window-all-closed`；mac 因平台惯例留驻）。

可是后台**已经有活要跑**：

- **design 的定时刷新**不是独立机制，它挂在 automations 的 `SchedulerService` 上，**每个工作区一个**，而这个调度器活在 app 进程里（`packages/shared/src/automations/automation-system.ts` 的 `startScheduler`；`packages/server-core/src/sessions/SessionManager.ts` 的 `automationSystems`）。
- **通知**在点击时会**现开一个窗口**去承接（`apps/electron/src/main/notifications.ts` 的 `handleNotificationClick`）——这本身就是"窗口不在时也要发生点什么"的证据。

所以今天"关掉窗口"等于**刷新停了、app 没了**。

### 1.2 被独立窗口逼出来

一旦 design 能开成**自己的窗口**（[设计方案](design-plan.md) §2.7）、甚至只剩一个看板窗口长挂，**"主窗口不在"就成了常态**。托盘就是回答"那 app 现在长什么样、怎么回去"的那块面。

### 1.3 Windows 上它更是必需

Windows / Linux 上**原生应用菜单是 `null`**（`apps/electron/src/main/menu.ts`，功能挪进了界面里的 Craft logo 菜单）。于是**没有窗口就没有菜单**——连"退出"都点不到。托盘在这些平台上不只是便利，是**唯一常驻的入口**。

---

## 2. 它是什么

**一块新的呈现面**，不是第五个入口对象（入口是工作区一级的一族：会话 / 来源 / 设计 / 项目 / tweaks / 自动化，尺子见 [设计方案](design-plan.md) §1.1）。用一句话定义它：

> **托盘 = 没有窗口时，app 在系统里的样子。**

平台对应：Windows / Linux 是系统托盘图标；macOS 是菜单栏状态项（Electron 的 `Tray` 两边都覆盖）。

### 2.1 三件职责（已定，按此顺序长）

| 顺序 | 职责 | 第一版 |
|---|---|---|
| ① | **常驻的壳**：唤起主窗口 / 会话，显示未读与运行中状态 | **做** |
| ② | **design 小应用的停靠点**：列出可独立运行的 design，点一个就开 / 切到它的窗口 | 后做 |
| ③ | **后台任务的面**：定时刷新、长任务、通知的落点（谁在跑、跑完没、点进去看） | 后做 |

三者共用同一个托盘，不新开第二个常驻入口。

### 2.2 它不是

- **不是第二个控制面板**：不在托盘里做会话列表、设置、完整导航——那些是窗口里的活。
- **不是配置文件**：托盘菜单读的是**当前状态**（工作区、窗口、未读），不新增 `tray.json` 之类的登记表（[约定大于配置](project-layers.md) §1）。
- **不是 macOS 的"仅菜单栏应用"**（隐藏 dock）——除非另有要求，dock 图标照旧。

---

## 3. 生命周期（已定：常驻）

**关掉所有窗口，app 不退出**（非 mac 也如此）。托盘因此有了存在的前提。

要改与要复用的：

| 项 | 现状 | 改动 |
|---|---|---|
| `window-all-closed` | 非 mac `app.quit()` | **不再退出**（`CRAFT_HEADLESS` 的行为不变） |
| 真正的退出 | `⌘Q` / `role: 'quit'`（mac 菜单） | **托盘菜单的 Quit** 也走同一条路；Windows / Linux 上它是唯一入口 |
| 自动更新安装前的退出 | 已有 `isQuitting` + `setBeforeUpdateInstallHook` | 不变（那是"真的要退"，不是"关窗"） |
| 单实例再启动 | `second-instance` 聚焦已有窗口 | 无窗口时它没有可聚焦的对象——托盘的"唤起"补上这一格 |
| macOS `activate`（点 dock） | 已是"无窗口时重建" | 不变；与托盘唤起**共用同一段逻辑** |

**一句要守的判断**：**关窗 ≠ 退出**。"退出"因此必须是**明确的动作**（托盘菜单 / `⌘Q` / 安装更新），而不是"最后一个人走了"的副作用。

### 3.1 关闭一个窗口：隐藏（已定）

改动**之前**库里有两套语义并存（app 窗口关闭即销毁，浏览器窗口关闭即隐藏）。**已定且已实现：app 窗口跟浏览器窗口，关闭 = 隐藏**：

| | app 窗口（`windowManager`） | 浏览器窗口（`browser-pane-manager`） |
|---|---|---|
| 关闭时 | **隐藏**：`preventDefault()` → 推 `CLOSE_REQUESTED` 给渲染层 → 弹层先关（`cancelPendingClose`）或确认 → `hideWindow()` → `hide()`；3 秒兜底与"渲染层不在"也走 hide | **隐藏**：`keepAliveOnWindowClose` → `preventDefault()` + `hide()` |
| 真正销毁 | 只在**退出**时（`isAppQuitting` 放行原生关闭） | 退出时 `performQuitCleanup()` → `destroyAll()` |
| `closed` 之后 | 从 `windows` map 移除（如今基本只在退出时发生） | 不销毁，窗口还在 |

**已定的取舍：app 窗口也"关闭 = 隐藏"**，与浏览器窗口一致——库里两套语义收敛成一套：**关闭一个窗口只是把它藏起来，销毁只发生在真的退出时**。

选它的理由：**视图状态原地保留**——面板布局、滚动位置、展开到一半的 UI，这些**没有落盘**的东西回来时还在（浏览器窗口之所以也这么干，是同一个收益）。

**要认的代价**：

- **每个"关掉"的窗口留下一个仍然活着的渲染进程**，内存随关掉的窗口数增长（隐藏 ≠ 没有）——**有上界，见 §3.7**。
- 隐藏的窗口**不在任务栏**里（这是对的），也不在屏幕上——"关掉之后还想看"就必须靠托盘（§3.2）。
- 两条链要按隐藏重算：窗口状态（§3.4）与浏览器窗口的收尾（§3.5）。

（走过、没采用的另一半：**关闭即销毁**——内存干净，但视图状态要靠"关闭时记路由 + 重放"补回来，而面板布局 / 滚动本来就没落盘，补不全。）

**常驻的前提是"有路回去"**：`WindowManager` 有一个 `resident` 开关，只有托盘建成（或 macOS 的 dock 在）时才为真。托盘建不出来时，关窗回到"真的关"——否则会出现"没窗口、也没托盘"的隐形进程（见 §3.6）。

### 3.2 点托盘：拉起哪一个

现状能用的原语，以及它们**真实**的含义：

| 原语 | 真实行为 |
|---|---|
| `getFocusedWindow()` | app 不在前台时是 `null` |
| `getLastActiveWindow()` | 名字叫 last active，实际是"聚焦的，否则 `windows` map 里的**第一个**"——而 map 是**创建顺序**。**它不是 MRU** |
| `focusOrCreateWindow(workspaceId)` | 按工作区：有就聚焦（minimized 先 restore），没有就新建 |
| mac `activate` | 已实现了"无窗口时按 `window-state.json` 重建" |

**策略**（点图标 = 默认动作）：

1. **有窗口**（无论可见还是隐藏）→ **show + focus 最近用过**的那个。
2. **一个窗口都没有**（全新启动，或都被销毁）→ 新建。

**隐藏模型下最容易踩的一处**：隐藏的窗口 `focus()` **不会把它显示出来**。库里现在没有这处——`focusOrCreateWindow` 只在 `isMinimized()` 时 `restore()`，而"隐藏"既不是最小化也不是销毁。所以必须**先 `show()` 再 `focus()`**。

要补的：

- **真正的 MRU**：现在没有（见上表）。加一个 `lastActiveWebContentsId`（窗口 `focus` 时更新，**隐藏前也留下**）——这是"点托盘拉起哪个窗口"唯一的权威答案。
- **把"拉起或新建"收成一个函数**，三个调用方共用：**托盘点击 / mac `activate` / `second-instance`**。这三个现在都只 `focus()`，对隐藏窗口无效；`activate` 甚至只在 `getAllWindows().length === 0` 时才建——有了隐藏窗口它既不建、也不显示。

（隐藏模型顺带省掉一件事：**不需要"关闭时记路由"**——窗口没被销毁，它本来在哪就还在哪。）

### 3.3 多窗口与多工作区

- 一个工作区**可以有多窗口**（`File → New Window`、会话"在新窗口打开"）；每个 managed 窗口对应一个工作区。
- `getWindowByWorkspace` 只返回**第一个**匹配——它就是"**该工作区的那一个窗口**"。§3.7 让这个身份成立：工作区**隐藏保留下来的那个**就是它，之后开的都是临时的。
- **托盘按工作区列**（`focusOrCreateWindow`）：工作区的那一个是它的家；**临时窗口不列**——它们是此刻开着的视图，由用户在应用内自己管。
- **浏览器窗口不能被当成"一个 app 窗口"**：它不在 `windowManager` 的 managed map 里，还常常 parked 在屏幕外 / 隐藏。托盘的"有没有窗口"必须**只看 managed windows**，否则会把 parked 窗口算进来，或误把它拉起来。

### 3.4 窗口状态：隐藏模型的账，和销毁正好相反

**省掉的那一半**：`getWindowStates()` 取的是 `getAllWindows()`（只滤 `isDestroyed()`）——**隐藏的窗口算在内**。所以"关掉所有窗口再从托盘 Quit，把 `window-state.json` 写成 `[]`"这个坑，**在隐藏模型下不存在**（那是销毁模型才要专门解决的事）。

**已定：启动一律显示，不恢复"收起"。** 曾加过一个**可见性标记**（`SavedWindow.hidden`），让被收起的窗口"重启后仍收着"——但那正好违背"**启动应用默认唤起主界面**"：打开 app 却什么都看不见，会被当成没打开。所以**去掉了这个标记**：`getWindowStates()` 只记工作区 / 边界 / 路由，`createInitialWindows()` 建出来的窗口一律 `show()`。**"收起"是运行时的语义，不跨重启。**

**已定：启动只开一个窗口——你最后在的那个工作区。** 不是"每条保存记录建一个"：有托盘之后，每个访问过的工作区都可能留下一个隐藏窗口（§3.7 的上界是"**每工作区**一个"，不是"全局一个"），全建的话打开 app 会一次冒出好几个。取 `lastFocusedWorkspaceId` 对应的那条（取不到就用第一条有效的），恢复它的**边界**与**路由**——所以"回到你离开的地方"仍然成立，只是只有一个窗口。

### 3.5 浏览器窗口的寿命跟谁走

**今天的事实**：一个工作区的**最后一个 app 窗口**被**销毁**时，`window.on('closed')` 触发 `workspaceWindowsClosedHandler` → `browserPaneManager.destroyForWorkspace(workspaceId)` 销毁该工作区的浏览器窗口（连带里面所有标签页）；若那是全局最后一个 app 窗口，再 `destroyAll()`。**macOS 上这段早退**（不销毁）。

**隐藏模型下这条链自然不跑**——因为关窗不再触发 `closed`。这正是想要的：**关掉一个 app 窗口不再连带毁掉浏览器窗口里的标签页**。但要确认收尾没丢：

- **真退出**已有人管：`before-quit` → `performQuitCleanup()` → `browserPaneManager.destroyAll()`。所以"退出时销毁浏览器窗口"是**已有的**，不依赖上面那条链。
- **于是那条链变成"几乎不触发"**（窗口被真的销毁基本只发生在退出时，而那时又被 `isAppQuitting` 挡掉）。**已定：不改成"该工作区没有 app 窗口了就收"**（含窗口内切换走的情况）——有托盘之后，那个隐藏的浏览器窗口是**可达的**（从托盘进该工作区就回到它），"没人能到达它"这条原始理由不再成立，而常驻本来就是要的。代价只是"你去过的每个工作区各留一个隐藏浏览器窗口"，上界 = 工作区数。

**注意**：隐藏只是"顺带不触发它"，并不代替"定义浏览器窗口何时走"——真退出时的 `destroyAll()` 才是那条定义。

### 3.6 单实例：托盘只有一个

**已有的**：`app.requestSingleInstanceLock()` 在 `index.ts` 顶部（`whenReady` 之前）——第二个实例拿不到锁就 `app.quit()`，并把命令行里的深链转给第一个实例（`second-instance`）。所以"再启动一次不产生第二个进程"原则上已经成立。headless 那条线另有独立后备（`lock-identity.ts` 注释点名的 WS 端口绑定），与托盘无关。

**一个必须先修的时序坑**：`app.whenReady().then(...)` 注册在 `if (!gotTheLock) … else …` 的**外面**。也就是说，拿不到锁的那个实例调了 `app.quit()` 之后，那个回调**仍然注册在案**——托盘若建在里面，就变成"赌 `app.quit()` 先赢还是 `whenReady` 先赢"。托盘是**建了就可见**的东西，不该赌时序：

- 把托盘的创建（连同整个初始化）**挂在 `gotTheLock` 上**——要么把 `whenReady` 的注册挪进 `else` 分支，要么在回调开头 `if (!gotTheLock) return`。

**托盘自身也要幂等**：`tray.ts` 持一个**模块级单例**（像 `registerLocalOriginHandler` 的 `WeakSet` 守卫那样），重复调用不叠图标——Electron 允许建多个 `Tray`，叠起来就是几个图标。

**退出时要 `destroy()`**：Windows 上没销毁的托盘图标会**残留到鼠标划过为止**。在 `before-quit` / `will-quit` 里销毁。

**第二个实例该做什么**：不是建窗口、更不是建托盘，而是走 §3.2 那个"**拉起或新建**"函数——有窗口（含隐藏）就 `show + focus`，一个都没有才新建。深链已经是这么走的（`handleDeepLink` → `focusOrCreateWindow`），正好共用同一处（含那条"先 `show()` 再 `focus()`"的修补）。

**几处边界**：

- **`CRAFT_HEADLESS` 不建托盘**（没有 GUI）。
- **开发期的多实例**（`CRAFT_INSTANCE_NUMBER`，每个实例一套 userData / 配置）：Electron 的单实例锁是**按 userData 目录**算的，所以并行实例各有各的锁、各有各的托盘——这是**预期**，别当 bug 修掉。
- **`CRAFT_SERVER_URL`（瘦客户端）已定：与全功能版行为统一**。它**有主窗口**——`createInitialWindows()` 只被 `isHeadless` 跳过，client-only 不跳过（`index.ts`），它是"连远端服务器的桌面壳"，**一样要有拉起主界面的能力**。所以它一样有托盘、一样常驻；只是它的留驻理由不是后台活（design 的定时刷新 / 调度跑在远端服务器那边），而是**通知 + 快速唤起**。

### 3.7 窗口上界：一个工作区留一个

隐藏模型的代价（§3.1）是"每个关掉的窗口留下一个渲染进程"。可开窗口的入口却不止一个——`File → New Window`、会话的"在新窗口打开"（`OPEN_SESSION_IN_NEW_WINDOW`）、深链 `?window=`——所以"**多窗口 × 只隐藏**"会**无上界地长**。这不是取舍问题，是缺一条规则。

**规则（已定并已实现）：一个工作区同时最多活一个窗口。**

- 关一个窗口时：它是该工作区**仅存的** → **隐藏**；否则 → **真的关**（销毁）。
- 于是**不需要定义"谁是主窗口"**——谁最后留下，谁就是工作区的那一个。
- 内存上界 = 工作区数；托盘菜单也回到"每工作区一条，加上当时还开着的临时窗口"。

**为什么是这条**：成熟应用只有两类模型——**单窗口常驻**（Slack / Discord / Spotify：只有主窗口，关 = 隐藏）与**多窗口文档**（浏览器 / 编辑器：关 = 销毁）。**"多窗口 + 只隐藏"没有先例，因为它正是唯一会单调增长的那种。** 这条也与本库既有的"**一个工作区一个浏览器窗口**"同构——窗口的身份是作用域，不是用途。

**代价（要认）**：临时窗口关掉后**丢视图状态**（面板 / 滚动）。它是临时视图，从来处（那个会话 / 工作区）能再开。

**由此一并定的两件**：`OPEN_SESSION_IN_NEW_WINDOW`（会话"在新窗口打开"）是**纯临时窗口**；未来 ② 的 design 独立窗口若不属于工作区主窗口，同样按临时处理。

## 4. 托盘菜单（第一版）

只做①常驻的壳，条目保持少：

- **工作区**——每条一个**工作区**，点它 `focusOrCreateWindow`：有窗口就显示（该工作区的那一个），没有就新建。**临时窗口不列**（它们的家是应用本身，不是托盘）。（原「New Window」条目已移除：托盘只管把工作区找回来，开新窗是应用内的事。）
- **未读 / 状态**——**第一版未做**：需要一个逐语言的新文案键（`lint:i18n:parity` 要求 7 个 locale 齐），留到文案定稿；计数来源是 `notifications.ts` 已经在维护的那一路。
- **分隔线**
- **退出**——真正退出 app（`app.quit()`，与 `⌘Q` 同一条路）。

**不做**（留给后面）：design 列表、运行中任务列表。

**点击行为按平台走**：Windows / Linux 上**左键 = 把 app 拉回来**（唤起最近用过的窗口，§3.2），**右键 = 菜单**；macOS 上点状态项**就是菜单**（那一处的惯例），要窗口从菜单里的工作区条目进。

**文案**：菜单项说人话、不解释机制（口径见 [术语与文案规范](vocabulary.md)）——是给"正在用这个图标的人"看的。

## 5. 代码位置

- **新增一个模块**：`apps/electron/src/main/tray.ts`，与 `menu.ts` 同级——它是**主进程面**，不走 RPC、不进渲染层。
- **创建时机**：`app.whenReady()` 之后（在 `index.ts` 里，与 `windowManager` / `notification` 初始化同处）；退出路径上销毁，避免残留图标。
- **macOS 用同一枚标记的两套单色稿**——`tray-black.png`（浅色菜单栏）/ `tray-white.png`（深色菜单栏），各自带 `@2x`；同样由 `icon.svg` 渲染（**替换 SVG 里的 `fill`** 为纯黑 / 纯白——比事后 tint 精确），几何与 Windows 那枚一致。按 `nativeTheme.shouldUseDarkColors` 选一张，并在系统主题变化时 `setImage` 换。**刻意不用 template image**：这是一对显式的黑白稿，保留标记自身的粗细，而不是被系统读成剪影。
- **Windows / Linux 从矢量渲染**：`resources/icon.svg`（24×24 的三条杠图形，本身即品牌色 `#9570BE`）→ 用 `sharp`（依赖里已有）渲染，**裁掉自带内缩**、按比例落位（`contain`，不压扁——这枚图形高瘦，硬塞成方形会走形）。选它是因为**实测**：同样渲染到 16px，它的边缘能量是应用图标的 **2.5 倍**（12604 vs 5084）——应用图标是带渐变的实心圆角方块，小尺寸下对比不足。它也正是 macOS 那对黑白稿的图形，**三平台同一枚标记**。
  - **Windows 带白色圆角底**（`tray-app.ico`）：一枚小的应用图块——**圆角半径 = 边长的 22%**、图形高 = 边长的 **60%**（宽度随它自身的比例 16:18；留出角部余量），这样在浅色与深色任务栏上都读得出来；四角透明，任务栏从圆角外透出来。图形**按 bbox 居中**、在矢量里排布（不贴位图，因此没有半像素取整漂移）。多尺寸 **16 / 20 / 24 / 32**（对应 100 / 125 / 150 / 200% 缩放）——Electron 自己的建议就是 Windows 用 ICO 且带齐这几档，单一尺寸的 PNG 被系统放大是发糊的另一半原因。
  - **Linux 用透明底**（`tray-app.png`，`@2x` 为 32px）：桌面环境的托盘区域样式各异，压一块白底不一定合适。
- **生命周期改动点**：`index.ts` 的 `app.on('window-all-closed')`（§3）。
- **与 §2.7 独立窗口的关系**：后面做②时，托盘的"design 停靠点"就是那些窗口的宿主/切入口；届时**读盘** `{workspace}/designs/` 取列表，不新增登记表。
