## 1. 把问题还原：一个「助理」到底解决什么

一个 agent 产品里，**每一轮对话都被三样东西绑住**：

1. **目录** —— 它有工作目录，所以它看得见代码、跑得了命令、受得了守卫。它也因此**只属于一个文件夹**。
2. **上下文** —— 它的知识活在这个会话的窗口里。窗口一关，学到的东西没有了。
3. **在场** —— 它只在你打开它、对着它说话的时候存在。

这三条不是缺陷，是**能力的前提**：正因为绑住目录它才能动手，正因为绑住上下文它才不胡编，正因为绑住在场它才不烦你。所以「助理」不是「更大的会话」——**助理是这三条绑不住的那部分工作**：

| 那一部分 | 它其实是 | Trae 的做法 | Craft 的做法 |
|---|---|---|---|
| **判断** | 跨会话地知道「现在值不值得做、上次为什么那么定」 | 分层记忆 + 命中注入 | 一份 `MEMORY.md`（注入 4.4%） |
| **派活** | 把一件活变成**不占用这条对话**的另一次执行 | `task_create` → 一条独立子会话 | `spawn_session` / `create_task`（DAG）+ 工作台 + 回话闭环 |
| **收活** | 活回来时**有人在场说一句** | `proactive_chat` + 子会话汇报 | hidden 唤醒消息 + 1.5s 合批（更细） |

**判据只有一条**：助理替你省掉了几轮。它答得多好是第二位的——一轮你本来要自己写的提示词，被它记住并自己发起，省的是整个轮次；答得再漂亮的被动回答，省的只是打字时间。

Trae 的三个机制（无路径项目 / 任务派活 / 两层记忆）不是三件事，是这同一个问题的三种答案。Craft 已经在中间那一列做得比它深；两端的差距全在「判断」一侧。

## 2. Trae 的答案（本机取证；新增两条)

底座事实见 [craft-bot-design.md](../pending/craft-bot-design.md) §1（`project_kind='global_assistant'`、`session_project` N:M、`task_create` + `spawn_create_task_subchat_loop`、`core_memory` 衰减、`scheduled_tasks`、`message_origin=proactive_chat`、`im_group`）。本文新增两条，都来自 `~/.trae-cn/` 的文本证据：

### 2.1 记忆有**四层**，按「什么时候需要」分，不是按主题分

| 层 | 形态 | 何时进上下文 |
|---|---|---|
| `project_memory.md` | 每个项目一份，人工可改的散文 | 进项目就注入（小） |
| `YYYYMMDD/topics.md` | 每天一段，append-only，**带 `session_id` 与时间戳** | **从不注入**，要用时去读 |
| `YYYYMMDD/session_memory_<id>.jsonl` | 每条一句话的结构化记录（见 2.2） | 从不注入，可被检索 |
| `builtin_skills/_shared/knowledges/**/SKILL.md` | **知识树**：每个节点一个文件，`description` 是路由信息 | **只注入 description**，正文按需加载 |

最后一条是它真正的架构点，写法很明确（`references/knowledge-format.md`）：

```
description: Covers <这个节点提供什么>.
  Navigate when: <具体任务场景>. Excludes: <不覆盖什么，指向兄弟节点>.
  Keywords: <模块名/类名/函数名/错误串>
```

**`description` 是唯一的触发机制**——不是摘要，是路由。这跟我们 skills 的 progressive disclosure 是同一条原理，我们已经在用（`~/.agents/skills` 三层），只是没用在「记忆」上。

### 2.2 每轮记录是**四个字段 + 一个指针**

`session_memory_6adf5a99ff2a9dd4255d7bd6.jsonl`：

```json
{"intent":"完成设备列表UI与交互重写、后端语义对齐及相关验证工作",
 "actions":["重写 ServerSettingsPage.tsx 中的设备列表 UI 与交互逻辑", "..."],
 "outcome":"所有需求功能实现完成，全部验证通过",
 "learned":["设备列表区分待连接邀请与已连接设备两类展示", "..."],
 "message_summary_time":"2026-10-26 22:12:08",
 "message_id":"6adf5a99ff2a9dd4255d7bd7"}   ← 指回原文那一轮
```

两件事值得单独记：

- **粒度是「一条」不是「一段」**：`learned` 是一个数组，每条一短句。批量注入、批量淘汰、批量核对都成立。
- **`message_id` 让记忆可证伪**：任何一条都能回到那一轮去看当时的原话。我们的 `MEMORY.md` 有时写 commit id，更多时候什么都不写。

**但这不等于我们要抄它的作业**：写这些是一个**每轮的 LLM 作业**（`extract_topics_and_update_memory`，输出 `no_update` 或 `new_memory`），代价是持续的 token 与写盘。我们不做作业的判断（§5）依然成立——要借的是它的**形状**，不是它雇的那个工人。

## 3. 先把「谁回答哪个问题」理清（功能交互）

在提议任何记忆结构之前，先看清已有机制怎么咬合。**结论是：Craft 的注入层本来就是「快照 + 路径 + 按需读」，欠的只是那份地图；而不是一套新的文件树。**

### 3.1 知识通道有五条，各有预算与唯一写者

| 通道 | 谁写 | 进上下文的部分 | 上限 | 失效方式 |
|---|---|---|---|---|
| 用户偏好 `preferences.json` | 人（界面） | 全文 | 很小 | — |
| 项目记忆 `MEMORY.md` | agent（`Write`/`Edit`） | **头部截断** | **总量 5,000 token**（`storage.ts:169`） | 超出即**不可见**（现为 4.4%） |
| 上下文文件 `CLAUDE.md`/`AGENTS.md` | 人/agent | 自动发现，按**位置**选（根 → 包） | 30 个 × 10KB（`system.ts:24,27`），**无总量** | 与代码漂移 |
| `sources` / `skills` | 人（配置） | 只有名字与 **description** | — | 描述与正文漂移 |
| 会话状态（权限/路径/plans/data） | 系统 | 全文 | — | — |

三条事实值得点出来：

1. **只有记忆这一条是「全量快照 + 硬截断」。** 上下文文件按**位置**路由（搬家就是信号，不会过期），skills 按**描述**路由（会过期，但过期了只是少加载一次，不是丢数据）。记忆是唯一一条**写进去而读不到**的。
2. **上下文文件那条通道没有总量上限**（30 × 10KB = 最多 300KB），真正有总量预算的只有记忆。所以「加预算」不是问题，**「把预算花在哪」**才是。
3. **记忆没有第二个读者**：`loadProjectMemory` → 注入（`claude-agent.ts:736` / `pi-agent.ts:334`）与漂移比较（`prompt-drift.ts:127`）是同一份字符串。任何拆文件的提案都会变成一个目录 watcher + 一句「哪个文件变了」的新措辞。

### 3.2 系统提示是**缓存前缀**，所以记忆必然是快照

会话第一轮把 preferences、co-author、项目块**钉住**（`prompt-drift.ts` 头部注释：每轮重打会打掉整段下游历史的缓存）。之后磁盘变了，**不重打，只发一句 notice**；`project-memory` 那句说的是：

> The project's MEMORY.md changed on disk after this session started — your system prompt still carries the copy taken when it began. **Read `<path>` for the newest notes.**

**这就是我们的「索引/正文分离」——早就有了**：快照进前缀，全文在路径上，要读就读。缺的不是架构，是**地图**：模型手里只有路径，「里面有什么」它不知道。

顺带一个盲点：漂移比较的是**被截断后**的字符串，所以 5,000 token 之后的任何改动，漂移检测**完全看不见**。

### 3.3 一件东西只能有一个写者（这是判新机制的第一条）

| 层 | 内容 | 写者 | 能否重建 |
|---|---|---|---|
| 盘上的文件 | 代码、文档、项目里的稿子 | 人 | 否（是事实） |
| 会话转录 | 每一轮原话、工具卡、计划 | 系统追加，**不可变** | 否（是事实） |
| 派生索引 | `creations`、看板列、搜索结果 | 从上一行重算 | **能** |
| 人的配置 | `preferences` / `config` / `permissions` / `statuses` / `labels` | 人（界面） | 否 |

**判据**：新机制必须落进其中一层，且只有一个写者。**只要它要求两处同步，它就是第二份描述，必然过期。**——这不是新规矩，`MEMORY.md` 与 Trae 项目的 `project_memory.md` 里各记过一次同一个教训（`classifyPrototypePath` 枚举整个文件夹、`APP_OWNED` 与写入者各写一份路径）。

### 3.4 判定表（两胜两负）

| | Trae | Craft | 判定 |
|---|---|---|---|
| **身份** | `project_kind='global_assistant'`，一个没有路径的「项目」；代价是到处 `if kind == global_assistant`，浮窗还得保证不绑项目 | `Session.role='bot'`，住在你已经打开的工作区里，一份配置、一份记忆 | **Craft 胜**，不要回头 |
| **派活** | 一个工具 `task_create` → 一条子会话；模型不能选模型以外的东西，图不存在 | `spawn_session`（一次性）+ `create_task`（DAG 上板、可审批、可停、可汇报）+ 工作台 + 回话闭环 | **Craft 胜**，已经抄完并做得更深 |
| **连续性** | 四层，按需加载，**每次只有 description 进上下文** | 一份 `MEMORY.md`，**头部截断** | **Craft 负**，但病因未定（§4.A 已撤回） |
| **收活** | `scheduled_tasks` + `proactive_chat`：**助理自己开这一轮** | `automations` 每次**造一个新会话**；bot 只能被「子任务结束」叫醒 | **Craft 负**，见 §4.B |

连续性这一格，用**仓库自己的算法**算（`large-response.ts`：`estimateTokens = len/4`，`estimateTokensDensityAware` 只在 base64 高密度时修正）：

```
MEMORY.md                 259,956 字符
仓库自己的“token”数        64,989（= len/4）
cap 5,000 ⇒ 保留字符数      20,000  ⇒ 可见 7.7%（不是 4.4%，见 §4.A 的撤回）
保留下来的那 20,000 字符里    31% 是中文 ⇒ 真实 token 约 7,600–9,700
```

最后一行是这一节真正值得记住的：**`maxTokens = 5000` 并不是 5,000 个 token 的上限**。它按字符算，而中文每字的价格是 ASCII 的 1.2–1.5 倍——所以这个文件每轮的真实开销是预算的 1.5–2 倍，而**没人知道**。

截断方向仍然是「新→旧」：被挡在门外的是最早那些段——也就是当初定下来的设计判断。

## 4. 该借的四件事

### A. 记忆（**已撤回**：这一节的前两版都不成立）

> 状态：撤回。链接、pin/drift、写作纪律的观察仍在；**结论没有了**。这一节留着，是为了让下一个人知道哪两条路已经走过、为什么错，而不是再走一遍。

#### A.0 我错在哪（三条，按严重程度）

1. **用自己的估计器冒充实测量。** 我按 `cjk×1 + ascii/3.8` 算出「≈112,600 token、可见 4.4%」，并在正文里写「实测」。仓库根本不用这个算法：`estimateTokens = ceil(len/4)`（`utils/large-response.ts:68`）。用仓库的算法，cap 5,000 保留的是 **20,000 字符 = 7.7%**。**两个数都不是真 token 数**——真 token 还要看 tokenizer。
2. **混着用两套单位做比较。** 说「目录 3,387 token，只花 5,000 预算的 68%」——3,387 是我那套（接近真实 token），5,000 是仓库那套（字符/4）。在同一个单位下它是 **1,959 / 5,000 = 39%**。一个跨单位的比例，无论结论对错都不该写出来。
3. **把症状当病因，还顺手把它合法化。** 设计意图是「一份小的、人工维持的 MEMORY.md（`kept under ~5000 tokens`）」。259KB 是**这条约定被违反了**，不是读取机制坏了。我提的「目录代替头部」会让一个无限增长的文件**看起来仍然工作**——等于把违约变成常态。这条比算错数字更严重，因为它会改变系统的激励方向。

#### A.1 已经核实的事实（可以直接用）

| 事实 | 证据 |
|---|---|
| `maxTokens` 是**字符数预算的一半**：`estimateTokens = len/4`，中文没有修正 | `utils/large-response.ts:68`、`projects/storage.ts:169` |
| 因此这个文件每轮的真实开销 ≈ **7,600–9,700 token**（31% 中文），而代码认为 5,000 | 实算（`kept 20,000 chars`）|
| 上下文文件通道同样按字符算：30 个文件 × 10KB **字符**，且**没有总量上限** | `prompts/system.ts:24,27,150,176` |
| 记忆是 pinned 的缓存前缀；磁盘变了只发 notice，不重打；notice 原文是「Read `<path>`」 | `agent/core/prompt-drift.ts` 头部注释 + `project-memory` 分支 |
| 漂移比较的是**截断后**的字符串 ⇒ 20,000 字符之后的改动它看不见 | `prompt-drift.ts:127` 与 `loadProjectMemory` 的返回值 |
| `automations` 的 prompt 确实**每次新建会话**（不是投进已有对话） | `SessionManager.ts:2101` → `executePromptAutomation`，日志 `Created session … from prompt action` |

**唯一可以确定叫「缺陷」的一条**：`maxTokens` 在中文内容上系统性低估 1.5–2 倍，所以「5000 token 预算」在任何中文项目里都不是 5,000。这是代码级事实，与记忆该多大无关，可以单独修（要么按 CJK 修正估计器，要么把上限改成按字符给定，别再叫它 token）。

#### A.2 仍然没有答案的两个问题（不该由我拍板）

1. **记忆应该多大？** 两个方向都有代价，而我现在没有证据选：
   - 收紧写入（超过 N 就拒写 / 强制把旧段移走）：**保住了「小」**，代价是模型在写的那一刻被拒绝——这与本项目「报告而不是拒绝」的判据相反。
   - 允许它大（目录 / 检索 / 分片）：**保住了「能写」**，代价是「小」这条约定事实上作废，而它是这个通道唯一的质量信号。
2. **如果允许它大，补偿放在哪？** 「目录」只解决「知道有这条」，「跨转录检索」只解决「原话在哪」。两者都不是免费的，也都不会让文件变小。

#### A.3 与我原结论无关、但站得住的两条观察

- 记忆是五条知识通道里唯一一条「写进去可能读不到」的（其余四条：按位置路由 / 按描述路由 / 系统直给 / 配置）。这条**不依赖任何数字**。
- `search_history`（跨转录检索，键是不可变消息 id）是独立于「记忆怎么组织」的另一件事：它回答「原话在哪」，不回答「该记什么」。

### B. 「没人打字的一轮」是一等公民

**原理**：助理省轮数的唯一通道是**它自己发起**。一个只会回应的东西，无论多聪明，省掉的都只是打字时间，不是轮次。而「自己发起」在实现上只要两个条件：**能收到活**（inbox）与**知道这一轮不是被要求的**（origin）。

**现状（两个都不完整）**：

- `automations` 的 prompt 动作：`apps/electron/resources/docs/automations.md:99` ——「Send a prompt to Craft Agent (**creates a new session for scheduled prompts**)」。于是一个每天 9:00 的「扫一遍昨天」在 30 天后留下 **30 个会话**，没有一条进入助理那唯一一条对话，谁也不记得前天扫过什么。
- `Message.origin?: 'user' | 'agent' | 'system'`（`dto.ts:538`）—— 三个值里**没有「它自己开工的」**。于是即使把定时活投进对话，界面也无法区分，模型也无从知道自己是被叫醒的还是被问的。
- Trae 两样都有：`scheduled_tasks`（cron/绝对/相对/时区）+ `message_origin ∈ {user, assistant_sub_chat, proactive_chat}`。

**借什么**：不是「定时任务」（我们有，还更强：事件总线 + cron + 限流 + matcher），是**投递目标**与**来源标记**。

**最小改法**：
1. `PromptAction` 加 `deliverTo?: 'new-session' | 'session'`（默认 `new-session`，旧行为不变），`session` 时在本工作区取 bot 会话（`bot:session` 已经是单飞的）并 `sendMessage`。
2. `Message.origin` 加 `'scheduled' | 'proactive'`；托盘与气泡各给一句话（「它自己开工的 · 9:00」），模型侧在提示里写明这一轮的来历。
3. 复用已有的唤醒机制（hidden 用户消息 + 合批 + 去重），不要再造一条投递路径。

**验收**：一条每天 9:00 的自动化，第二天在**同一条**对话里多一轮、标记「它自己开工的」、会话列表**没有**新会话；关掉它之后不再出现。

**为什么现在做**：工作台刚刚落定了「进行中全列 / 已完成最新 8 张」（`d16865229`）——那条判断的前提是「一张桌子是现在的表盘」。如果定时活继续造会话，这个表盘会被自动化灌满，而灌满它的东西恰好是没人派过的活。

### C. 一个不依赖窗口的地址

**原理**：在场性。Trae 的 `im_group` 是一种工作区、`resolveAssistantImSession` 是一条通道——这些都在回答「你不在电脑前时，那句话去哪」。

Craft 的底座已经有：`messaging-gateway`（Telegram/WhatsApp/飞书）+ 自动化里已经在用的 `telegramTopic` 路由。缺的是**把地址绑给「助理这个身份」而不是某一条会话**。

**借什么**：不借渠道，借**不变量**——同一个地址，永远落进同一条对话，不为每条消息造会话。

**最小改法**：`Session.role === 'bot'` 的会话可以挂一个通道；入站消息走 B 的同一条投递路径（`origin: 'user'`，但带 `fromChannel`）。这与 craft-bot-design.md 的 M4 是同一件事，**只是理由变了**：不是为了「多一个入口」，是为了「助理有一个不随窗口开关而消失的地址」。

### D. 每条记忆带出处与失效条件（借 schema，不借作业）

**原理**：一份只增不减的记忆，最终一定会变成没人读的档案。让它敢增长的只有两件事：**能核对**（指回原文）与**能淘汰**（写明什么情况下它不再成立）。

**借什么**：Trae 的 `message_id`（每条记录指回那一轮）。**不借**它的 `extract_topics_and_update_memory` 作业、不借 `core_memory` 的 LRU/LFU/指数衰减表（那是「上下文装不下」的解法，我们有 compaction，先有证据再引入）。

**最小改法**：一条提示词纪律，加上目录天然带给它的机械检查——每段标题保持「一句结论 \+（日期 \+ 出处）」的形状（现在 154/156 已带日期，多数带 commit），“什么时候该被推翻”写在正文第一句。这不是新机制，是把 `MEMORY.md` 里已经在做（但只做了一半）的事变成规则。

**为什么它跟 A 绑在一起**：A 把每段的「在地图上的成本」降到 22 token，于是留在地图里变得便宜；但**便宜不等于值得**——如果因为便宜就什么都留着，目录本身迟早涨到 5k。D 是那条淘汰线：有出处的段可以把出处变成判断（会话还在吗？commit 被回退了吗？），没出处的段只能永远留着。

> **不新增文件、不新增字段。** 上一版这里写的是 `memory/*.md` 的 frontmatter 格式——那已经随 §4.A 一起作废。

## 5. 不该借的（以及这次为什么仍然成立）

| 不做 | 理由（这次的证据） |
|---|---|
| `project_kind='global_assistant'` | 它的便宜是复用 project 表，代价是**每个读项目的地方都要记得有个例外**（「GlobalAssistant has no workspace path」就是漏掉一次的结果）。我们的 `role` 不产生例外，且路径守卫一个字都不用改。**这一点只有一次机会**：一旦为了「助理要有个家」再造一种项目/工作区，就会重新长出一整套要配的东西（我们在 §3.1.1 已经付过一次学费）。 |
| 云端用户画像 + 本地读默认关 | 本地优先。「它记得你什么」必须是一行你能打开改的字。 |
| `core_memory` 衰减库 | 没有「上下文装不下」的证据就先加一层要调参的记忆库，等于用调参代替设计。 |
| 每轮 LLM 摘要作业 | 义务加在过程中，产出多半没人回头读；要用也是**检索替代预写**（§4.A.3）。 |
| `task` 作为唯一开工入口 | 他们的助理没有看板，所以任务表兼了看板。我们两样都有，一个开工工具服务一种形状（一次性 vs 一张图）。 |
| 助理持有转发权（多跳） | 不可审计、易死循环。 |
| 常驻悬浮球 | 常驻面只允许一个（托盘）。要有也是**有租约的胶囊**，没活时不存在。 |

## 6. 一个可选的中间态：跨工作区的**读**

旧文档把跨工作区整条线拆了（delegate/grant/A2A）——**判定仍然对**：真实的场景是「在这儿做完」，不是「交给那边」。但拆的时候连带拆掉了**读**，而 Trae 的跨项目能力本来就停在读历史这一个动作上。

低成本补法（只是候选，不是建议立刻做）：助理的上下文里加一段**别的项目的记忆索引**——一行一个项目：名字 + `MEMORY.md` 的第一行。它给的是「别处有什么」的判断力，**不给**「去那边动手」的能力。风险是身份变模糊（你说「助理」时指的是哪个区的那一个），所以只有在用户明确要「多个项目一起看」时才开。

## 7. 现在能确定的只有两件

**一，B（把定时活投进同一条对话）**：它是唯一一条**代码与文档都印证、且不依赖任何估算**的缺口（`SessionManager.ts:2101` 确实每次新建会话）。做与不做是产品选择，但事实没有歧义。

**二，`maxTokens` 在中文上不是 token 上限**（§4.A.1）：`estimateTokens = len/4` 让「5000 token」在中文项目里变成 7,600–9,700。这是可以单独修的代码问题，与「记忆该多大」无关。

**至于记忆该怎么组织——没有结论。** 前两版方案（目录树 / 目录代头）都错了，错因已写在 §4.A.0。下一版应该从「记忆该不该这么大」这个产品问题开始，而不是从文件布局开始。
